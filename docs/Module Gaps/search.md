# Module: Search (webapp)

## 1. Purpose & Current Usage

- `src/features/search/` implements the global Cmd+K search: a modal overlay (`SearchModal.tsx`) with a text input (`SearchInput.tsx`), a debounced query against the backend `/search` endpoint, a results list grouped into "Modules" (quick-nav chips) and "Results" (`SearchResults.tsx` / `SearchItem.tsx`), and a "Recent" list shown when the query is empty (`RecentSearches.tsx`).
- Trigger: `src/components/layout/MainLayout.tsx:19-28` registers a global `keydown` listener for `Cmd/Ctrl+/` that calls `openModal()` from the Zustand store. `src/features/sidebar/Sidebar.tsx:124` also calls `openModal()` (presumably from a search icon/button in the sidebar). `MainLayout.tsx:59` mounts `<SearchModal />` once at the layout root, so it's available on every authenticated page.
- Data flow: `useSearch` (`src/features/search/hooks/useSearch.ts:7-15`) wraps `searchGlobal` (`src/features/search/api/search.ts:12-13`) in a React Query, keyed by the raw query string, `enabled` only when non-empty, with `keepPreviousData` and a 30s `staleTime`. `useRecentSearches`/`useSaveRecentSearch` (`src/features/search/hooks/useRecentSearches.ts`) hit `/search/recent` (GET/POST) and invalidate on save.
- State: `src/features/search/store/search.store.ts` is a minimal Zustand store holding only `isOpen` — no query/result state is global, it all lives in local `SearchModal` state.
- Dead/unused: the `SearchResultItem.permissions: string[]` field (`src/features/search/types/search.types.ts:9`) is declared on the type but is never read anywhere in `SearchItem.tsx`, `SearchResults.tsx`, or elsewhere in `src/features/search/` — it is plumbed through the type only, not used for UI or logic (see §3).

## 2. Intended / Ideal Usage

- Open instantly via keyboard shortcut from anywhere, type a query, see debounced results within ~200ms with in-flight requests cancelled, navigate with arrow keys with the selected item auto-scrolled into view and announced to assistive tech, and only ever see results the user is actually permitted to view (mirroring backend RBAC, not just displaying an unenforced `permissions` array).
- The modal should trap focus while open (Tab/Shift+Tab cycle only within the dialog), restore focus to the trigger element on close, and expose a proper `combobox`/`listbox` ARIA relationship (`aria-controls`, `aria-activedescendant`) so screen readers announce the highlighted result as arrow keys move.
- Errors (network failure, 401, 500) should surface a visible message in the modal rather than leaving the body blank.

## 3. Cross-Module Connections

- **Depends on**: backend `GET /search` and `GET/POST /search/recent` (`src/features/search/api/search.ts:12-19`), whose access-control gap is already documented in `brello_server/docs/Module Gaps/global-search.md` (no per-result permission filtering; 15+ modules unindexed; no reindex job). Also depends on `apiClient` (`src/lib/axios.ts`) for auth header injection and 401 handling, and on `useDebounce` (`src/hooks/useDebounce.ts`).
- **Depended on by**: `MainLayout.tsx` (mounts the modal globally) and `Sidebar.tsx` (opens it), i.e. it's a cross-cutting shell feature reachable from every route.
- **Missing/expected connection — misleading trust signal**: the frontend type `SearchResultItem.permissions` (`search.types.ts:9`) exists specifically to carry the backend's per-result permission data, but `SearchItem.tsx` (lines 37-55) renders every result identically — no lock icon, no "restricted" badge, no filtering by `permissions`. This means the UI does **not** actively mislead users with a false "this is permission-checked" visual (no lock/shield icon is shown), but it also means the `permissions` field the backend does return is silently dropped by the client, so there is no client-side defense-in-depth either. Combined with the backend's confirmed lack of enforcement, any authenticated user typing in this modal can see role/reimbursement/company-policy results they shouldn't — the frontend has the data needed to at least gray-out/hide such items client-side and does not use it.
- The generic `Shield` icon in `SearchItem.tsx:9,32` is mapped to `entity_type: 'role'` (an icon for the "Roles" entity), not a permission/lock indicator — worth noting so it isn't mistaken for a security affordance during review.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)
- The `permissions` field returned by the backend is typed but has no consumer anywhere in the search feature (`search.types.ts:9` vs. `SearchItem.tsx`) — there is no abstraction (e.g. a `useHasPermission`/`RestrictedBadge`) for turning that data into a client-side visual cue, so the one piece of security-relevant metadata the API sends is a no-op on the frontend. Matters because it's the cheapest place to add a stopgap (hide/gray out) while the backend enforcement described in the server-side audit is still missing.
- `SearchModal.tsx` owns query state, debounce, selection index, keyboard handling, and navigation/recent-search side effects all in one 157-line component with no sub-hook (e.g. `useSearchModal`) — mixes UI composition with business logic, making it harder to unit test the keyboard-nav/selection logic in isolation.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling, unsafe assumptions)
- No error state is surfaced: `SearchModal.tsx:43` destructures only `{ data: searchData, isFetching }` from `useSearch`, ignoring `isError`/`error`. If `/search` fails (network error, 401, 500), `searchData` stays `undefined`, and the JSX at `SearchModal.tsx:134-145` (`hasQuery ? (searchData && (...)) : (...)`) renders nothing — the modal body goes blank with no message, indistinguishable from "still loading" or a bug. Matters because users get no feedback that search is broken.
- `SearchResults.tsx:22-28` returns the "No results found" empty state as soon as `results.length === 0`, before ever checking `data.data.modules` — if the backend returns module chips (e.g. "Jump to Employees/Projects") alongside zero text-match results, those chips are silently dropped. Matters because the "Modules" quick-nav (a distinct, query-independent affordance) becomes unreachable whenever a query has no result matches.
- `RecentSearches.tsx:14` guards with `items?.length === 0` but the prop type (`RecentSearchesProps.items: RecentSearchItem[]`) is non-optional and `SearchModal.tsx:144` always passes `recentItems?.data ?? []`, so the optional-chaining is dead defensive code masking an inconsistent contract (prop typed as required array but treated as possibly-undefined).
- `SearchItem.tsx:52` does `item.entity_type.replace('_', ' ')`, a non-global `replace`, so any entity_type with more than one underscore (e.g. a hypothetical `company_policy_doc`) would render only the first underscore as a space — currently harmless for existing keys (`company_policy`, `role`, etc.) but a latent bug if new entity types are added.

### Technical (performance — debounce/cancellation of in-flight requests as user types — accessibility — keyboard nav, focus trap, screen reader labels — test coverage)
- Debounce is a flat 200ms (`SearchModal.tsx:33`, via `src/hooks/useDebounce.ts`) with no explicit request cancellation in the search feature itself; cancellation relies entirely on React Query's implicit behavior of passing the `AbortSignal` through to `searchGlobal(query, signal)` (`api/search.ts:12-13`) when the query key changes — there is no minimum-character gate (e.g. requiring 2+ chars before firing), so single-keystroke queries still hit the backend.
- No focus trap: the dialog (`SearchModal.tsx:116-156`) has `role="dialog" aria-modal="true"` but no focus-trap implementation — Tab/Shift+Tab from the input is not intercepted, so keyboard focus can leave the modal into the (visually hidden but still-mounted) page behind it, violating the `aria-modal` contract. Matters for screen-reader and keyboard-only users.
- No `aria-activedescendant`/`aria-controls`/`aria-expanded`/combobox role wiring between `SearchInput`'s `<input>` (`SearchInput.tsx:17-27`) and the `role="listbox"` in `SearchResults.tsx:31` — arrow-key selection changes (`SearchModal.tsx:100-108`) are purely visual (`isSelected` CSS class in `SearchItem.tsx:40`), so a screen reader user gets no announcement of which result is currently highlighted.
- Selected item is never scrolled into view: `SearchResults.module.scss` sets `overflow-y: auto; max-height: 400px` on `.container`, but neither `SearchItem.tsx` nor `SearchResults.tsx` calls `scrollIntoView`/uses a ref keyed to `selectedIndex`, so arrowing down past the visible viewport moves the logical selection off-screen with no visual feedback.
- No focus restoration on close: closing via Escape/overlay-click/selecting a result (`closeModal()` calls throughout `SearchModal.tsx`) never returns focus to the element that opened the modal (e.g. the sidebar search trigger), which is a standard modal-dialog a11y requirement.
- Zero test coverage: no `.test.`/`.spec.` files exist anywhere under `src/features/search/`, and none exist anywhere else in the repo either (confirmed via repo-wide search) — the debounce/keyboard-nav/selection-reset logic in `SearchModal.tsx` (lines 25-39, 91-111) has no regression protection.

## 5. Top 3 Priorities

1. **Wire the unused `permissions` field into a client-side safeguard** (`search.types.ts:9`, `SearchItem.tsx`) — until the backend enforces per-result RBAC (per the server-side audit), the frontend should at minimum hide/gray-out results the current user lacks permission for using the data already being sent, rather than rendering every result identically.
2. **Surface search errors in the UI** (`SearchModal.tsx:43,134-145`) — silently blank results on API failure is a basic reliability gap that's a one-line fix (destructure and branch on `isError`).
3. **Add focus trap + `aria-activedescendant` combobox wiring** (`SearchModal.tsx:116-156`, `SearchInput.tsx`, `SearchResults.tsx:31`) — the modal currently fails standard keyboard/screen-reader dialog accessibility despite advertising keyboard shortcuts in its own footer hint.
