# Module: Leave Management (webapp)

## 1. Purpose & Current Usage

- `src/features/leave-management/` is an **admin-facing operational UI** for two things: (1) reviewing/approving/rejecting employee leave requests, and (2) viewing and manually adjusting employee leave balances. It is **not** a leave-policy/type configuration UI — despite the name, it contains no leave-type or leave-rules editing.
- Components: `LeaveBalanceView.tsx` (searchable/sortable/paginated table of employee balances, department + year filters, `src/features/leave-management/components/LeaveBalanceView.tsx:16-210`), `EmployeeBalanceModal.tsx` (per-employee balance breakdown with inline "allocated days" edit, `EmployeeBalanceModal.tsx:16-120`), `LeaveRequestsListView.tsx` (paginated request list with inline approve/reject, `LeaveRequestsListView.tsx:18-189`), `RequestDetailsModal.tsx` (drill-in request detail with approve/reject, `RequestDetailsModal.tsx:18-136`).
- Data layer: `src/hooks/useLeaveBalances.ts` and `src/hooks/useLeaveRequests.ts` (React Query) wrapping `src/api/leaveBalances.ts` and `src/api/leaveRequests.ts` (axios calls to `/leave-balances/*` and `/leave-requests/*`). Shared types in `src/types/leaveRequest.ts`.
- Actual usage: mounted at two routes in `src/routes/adminRoutes.tsx:170-185` — `attendance/balance` → `LeaveManagementPage` (`src/pages/attendance/LeaveManagementPage.tsx:4,13`) gated by `ModuleCode.LEAVE_BALANCE`, and `attendance/requests` → `LeaveRequestsPage` (`src/pages/attendance/LeaveRequestsPage.tsx:4,16`) gated by `ModuleCode.LEAVE_REQUESTS`. Both are real, reachable admin routes (nav is DB-driven via the platform module table, not a hardcoded sidebar list).
- **Dead code:** of the 12 exported functions in `src/hooks/useLeaveBalances.ts`, only `useLeaveBalances` and `useUpdateLeaveBalance` are consumed anywhere in `src/`. `useMyLeaveBalance`, `useEmployeeLeaveBalance`, `useLeaveBalanceLedger`, `useInitializeBalance`, `useBulkInitializeBalance`, `useAdjustBalance`, and `useRecomputeBalance` (plus their backing API functions in `src/api/leaveBalances.ts:94-183`) have zero call sites app-wide — confirmed via repo-wide grep. Similarly `usePendingApprovals` in `src/hooks/useLeaveRequests.ts:20-25` is unused (the list view calls the generic `useLeaveRequests` with no status filter instead).
- No test files exist anywhere under `src/features/leave-management/` (confirmed via find).

### `leave-management/` vs `leave/` — not a duplication, but an unclear split
- `src/features/leave/` (components: `LeaveTypesCard.tsx`, `LeaveRulesCard.tsx`; hook `useLeaveConfig.ts`; api `leaveConfig.ts` wrapping `GET/POST/PUT /leave-configs*`) is the **leave-policy configuration wizard** — total leave days, per-type allocation/accrual, and approval/backdating rules. This is the frontend counterpart to the backend `leave-config` module described in `brello_server/docs/Module Gaps/leave-config.md`.
- `src/features/leave-management/` is the **operational request/balance console** described above — it never touches `/leave-configs*` endpoints at all.
- This is very likely an intentional split (config vs. operations) but the naming is confusing/inverted: `leave-management` sounds like it should own policy management, while `leave` (which reads like the employee-facing module the sibling audit is covering) is actually the admin config wizard. Worth a rename for clarity (e.g. `leave-policy-config` and `leave-operations`).

## 2. Intended / Ideal Usage

- An HR/admin user opens `attendance/requests` to see a live, accurate count and list of pending leave requests, drills into a request to see full context, and approves/rejects with a real, employee-visible comment/reason that also updates the affected balance atomically.
- The same user opens `attendance/balance` to audit each employee's per-type allocation vs. consumption for a given leave year, drilling into an employee to make one-off manual corrections (with the ledger/adjustment endpoints already built in `api/leaveBalances.ts` providing an auditable trail) when the automatic accrual/consumption is wrong.
- Both flows should give clear success/failure feedback per action, and any approve/reject click should be an intentional, confirmable action given it directly affects employee pay/leave records.

## 3. Cross-Module Connections

- **Depends on:** `useDepartments` (`src/features/department/hooks/useDepartments`, used for the department filter in `LeaveBalanceView.tsx:8,39`), shared `DataTable`/`Select`/`Dialog`/`Button` components, `apiClient` (`src/lib/axios.ts`), and backend `leave-request`/`leave-balance` modules.
- **Depended on by:** nothing else in the frontend imports from `leave-management/` — it's a terminal/leaf feature (only consumed by its two page wrappers).
- **Missing/expected connection — does NOT surface the backend "current policy" drift risk.** The backend audit (`brello_server/docs/Module Gaps/leave-config.md`) flags that `GET /leave-configs/current` (`findCurrent`) ignores `status` and can return an un-activated draft, while `leave-request`/`leave-balance` enforce `status = ACTIVE` independently. **`leave-management/` never calls `/leave-configs/current`** — that call lives entirely in the sibling `src/features/leave/` feature (`src/api/leaveConfig.ts:31-33`, `src/features/leave/hooks/useLeaveConfig.ts:16`). So this specific feature isn't the one at risk of showing a stale "current policy" — that risk belongs to `leave/`'s config wizard, not to the balance/request views audited here. However, `leave-management/`'s balance table does display `leave_type_name`/`total_allocated` figures that were computed from whatever config *was* ACTIVE at balance-initialization time (`api/leaveBalances.ts:31-41`), and there is no UI indicator anywhere in this feature of which policy version those figures trace back to — an admin reconciling `attendance/balance` against the config wizard's "current policy" screen has no way to tell if they're looking at the same policy generation.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)
- **`leave-management` vs `leave` naming inversion** (see §1) — no code coupling issue, but a real discoverability/maintenance risk: a developer told to "add a leave policy field" would reasonably start looking in `leave-management/` and find nothing relevant there.
- **~60% of the balance API/hook surface is unreferenced dead code** (`src/hooks/useLeaveBalances.ts` — `useMyLeaveBalance`, `useEmployeeLeaveBalance`, `useLeaveBalanceLedger`, `useInitializeBalance`, `useBulkInitializeBalance`, `useAdjustBalance`, `useRecomputeBalance`; also `usePendingApprovals` in `useLeaveRequests.ts:20-25`). This means the ledger/adjustment/recompute audit trail that the backend supports (`recomputeLeaveBalance` even returns a `drift_detected` flag, `api/leaveBalances.ts:171-183`) is not exposed anywhere in the UI — `EmployeeBalanceModal` only lets an admin silently overwrite `allocated_days` via `useUpdateLeaveBalance` with no view into the ledger history that would explain the current number.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling)
- **Hardcoded, non-live pending-request count in page subtitle.** `LeaveRequestsPage.tsx:12`: `subtitle="You have 7 Pending Leave Requests that need action!"` — the "7" is a static string, not derived from `response?.pagination?.total` or any query; it will show "7" regardless of the actual pending count. This is user-facing and directly misleading.
- **No error handling on approve/reject/update mutations.** `useApproveLeaveRequest`/`useRejectLeaveRequest` (`src/hooks/useLeaveRequests.ts:35-59`) and `useUpdateLeaveBalance` (`src/hooks/useLeaveBalances.ts:134-146`) have no `onError`, and the global `apiClient` interceptor (`src/lib/axios.ts:85-89`) only handles 401 refresh — there is no toast/notification system wired in (no `MutationCache`/`QueryCache` `onError` in `src/lib/react-query.ts:3-9` either). A failed approve/reject/balance-update (e.g. a validation error from the backend) fails completely silently: the button click does nothing visible, and in `RequestDetailsModal.tsx:36-38` the modal simply stays open with no message.
- **One-click approve/reject with a fabricated audit reason, no confirmation.** `LeaveRequestsListView.tsx:41-47`: clicking Approve/Reject from the list immediately calls the mutation with a hardcoded `comment: 'Approved from list view'` / `rejection_reason: 'Rejected from list view'` — these placeholder strings become the persisted audit/approval comment shown to the employee, and there is no confirmation step for what is effectively an irreversible HR action.
- **Non-functional "Filters" button.** `LeaveRequestsListView.tsx:156-159`: `<Button variant="outline" className={styles.filterBtn}><Filter size={16} />Filters</Button>` has no `onClick` and no filter panel — dead UI affordance that looks interactive.
- **Search has no debounce.** Both `LeaveBalanceView.tsx:161` and `LeaveRequestsListView.tsx:150` bind the search `<input>` directly to state that is part of the React Query key (`useLeaveBalances`/`useLeaveRequests` params), so every keystroke fires a new network request.

### Technical (performance, security, accessibility, test coverage)
- **No keyboard accessibility on interactive controls.** All sort headers, row actions, and approve/reject/edit icons are plain `<div>`/icon `onClick` handlers with no `role="button"`, `tabIndex`, `onKeyDown`, or `aria-label` — e.g. `LeaveBalanceView.tsx:67,97,106,140`, `LeaveRequestsListView.tsx:122,125,130`, `EmployeeBalanceModal.tsx:93,95,103`. None of these are reachable or activatable via keyboard, and icon-only actions (Eye/X/Check) have no accessible name for screen readers.
- **Zero automated test coverage** for the entire feature (no `*.test.*`/`*.spec.*` files under `src/features/leave-management/`, confirmed by search) — the approve/reject/balance-edit flows that directly mutate pay-adjacent employee data ship with no regression safety net.
- **No client-side bound on manual balance edits.** `EmployeeBalanceModal.tsx:83-89`: the inline "allocated days" edit input has no `min`/`max` and no validation before calling `useUpdateLeaveBalance` — a negative or absurd value can be submitted directly from the UI (whether the backend rejects it is outside this feature's code, but the UI gives no client-side guard or warning).

## 5. Top 3 Priorities

1. **Fix the hardcoded "7 Pending Leave Requests" subtitle** (`LeaveRequestsPage.tsx:12`) — it is a shipped, user-visible falsehood that costs one line to fix (bind to the real pending count) and undermines trust in the whole page.
2. **Add error feedback (toast/inline error) to approve/reject/balance-update mutations** and replace the hardcoded "Approved/Rejected from list view" audit strings with either a required reason prompt or a confirmation step — right now failures are invisible and the persisted approval trail is fake filler text, which matters for an action that affects employee pay and leave records.
3. **Rename `leave-management/` and `leave/` to reflect what they actually are** (config wizard vs. operational console) and/or surface which policy generation a displayed balance was computed against — not because the code is broken, but because the current naming actively points developers and reviewers at the wrong module when reasoning about leave-policy correctness (as this audit's own initial hypothesis, corrected above, illustrates).
