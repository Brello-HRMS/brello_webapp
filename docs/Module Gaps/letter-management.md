# Module: Letter Management (webapp)

## 1. Purpose & Current Usage

The frontend provides HR-side setup/issuance screens and one employee-facing screen for the letter-management module:

- **Setup (admin)** — `src/pages/letter-management/LetterSetupPage.tsx` is a tab shell (Settings / Categories / Signatories / Templates) mounted at `letter-management/setup` (`src/routes/adminRoutes.tsx:117-124`), gated by `RequireAccess module={ModuleCode.LETTER_TEMPLATES}`.
  - `CategoriesPage.tsx` — CRUD + archive/unarchive for `LetterCategory`.
  - `SignatoriesPage.tsx` — CRUD + set-default + archive/unarchive for `Signatory` (name, designation, signature image at creation).
  - `LetterSettingsPage.tsx` — org-wide numbering prefix, date format, default signatory.
  - `TemplatesPage.tsx` + `TemplateEditorPage.tsx` (routes `letter-management/templates/new` and `/:id`, `adminRoutes.tsx:125-140`) — plain form-based template editor (`TemplateForm.tsx`): heading, `paragraphs[]`, `bullet_list[]` with `{{variable}}` placeholders (`InsertVariableDropdown.tsx`), optional salary table flag, optional signatory, publish/duplicate/archive workflow, live preview (`TemplateLivePreview.tsx`).
- **Issuance (admin)** — `IssuedLettersPage.tsx` (route `letter-management/issued-letters`, gated by `ModuleCode.LETTER_ISSUED`) — 3-step `GenerateLetterDrawer` (employee → published template → resolve/preview → generate), grouped-by-employee table, per-employee letters drawer, PDF preview/download.
- **Employee self-service** — `src/pages/employee-letters/MyLettersPage.tsx` (route `letters/me`, `src/routes/employeeRoutes.tsx:10`) — lists the signed-in employee's issued letters (`MyLetterCard.tsx`), with preview, download, and **acknowledge** actions.

### Corrections to prior backend-side findings (verified against current frontend code)
- **Acknowledge UI does exist.** Contrary to the assumption that `acknowledgeMine` has zero frontend UI: `MyLetterCard.tsx:40-49` renders a "CheckCircle2" Acknowledge icon-button whenever `delivery_status !== 'ACKNOWLEDGED'`; `MyLettersPage.tsx:37-42` wires it to `useAcknowledgeLetter()`; the hook (`hooks/useIssuedLetters.ts:134-148`) calls `acknowledgeMyLetter` (`api/issuedLetter.ts:48-49`, `POST /me/:id/acknowledge`) and invalidates `['my-letters']` on success. This gap does not exist on the frontend — flag as resolved/incorrect assumption.
- **Signature image is confirmed never rendered**, and the frontend code says so explicitly: `src/features/letter-management/utils/getInitials.ts:1-10` is a developer comment stating `signature_document_id` would need a signed-URL lookup that no hook in this codebase performs yet, so "we render the signatory's initials instead of fetching/rendering the actual signature image." `SignatoryCard.tsx:31-33` only renders `getInitials(name)` in an avatar div — there is no `<img>` anywhere in `SignatoryCard`, `SignatoriesPage`, `TemplateForm`, or any preview component that reads `signature_document_id`.
- **No self-service "request a letter" flow** — confirmed; `src/pages/employee-letters/` contains only `MyLettersPage.tsx`, no request/create UI, and no such route exists in `employeeRoutes.tsx`.
- **Templates are a plain form, not a block-based visual designer** — confirmed; `TemplateForm.tsx` is a single RHF form with `heading` (Input), `paragraphs`/`bullet_list` (repeatable `TextArea` rows), a checkbox, and a `Select`. No TipTap/rich-block editor exists anywhere under `src/features/letter-management/`.

## 2. Intended / Ideal Usage

An HR letter-issuance UI should let admins: (1) maintain a clean, versioned template library organized by category, (2) manage signatories including their real signature images end-to-end (upload, preview, and replace), (3) generate/issue letters against an employee with a review step that renders exactly what will be produced (including the actual signature), and (4) give employees a lightweight self-service surface to view, download, and acknowledge letters, with acknowledgment feeding back into the admin's issuance view. Permission boundaries should let an org scope categories/signatories/settings/templates administration separately from who can actually generate/issue letters.

## 3. Cross-Module Connections

- **Depends on**: `useModuleAccess`/`PermissionGate`/`RequireAccess` (RBAC), `DataTable`/`Select`/`Dialog`/`WarningModal`/`ListControls` common components, `apiClient` (`src/lib/axios`), employee search (`GET /letter-management/employees/search`) which presumably comes from the employee directory module, `resolveAssetUrl` for signed download URLs.
- **Depends on (missing)**: a generic "document id → viewable image" hook/component. The codebase has one for employee avatars (already-URL-shaped) but nothing that resolves a bare document id to a signed URL and renders it — `getInitials.ts:1-10` calls this out by name (`DocumentRender`, used elsewhere e.g. `FeedbackDetailDrawer`) as the intended but never-wired path for signatures.
- **What depends on this**: the employee sidebar/nav entry that surfaces `letters/me`; any org onboarding flow that needs `LetterSettings.default_signatory_id` configured before letters can be generated (via `LetterSettingsPage`).
- **Missing/expected connections**: no link from `IssuedLettersPage` back to a per-employee acknowledgment/audit trail beyond the delivery-status badge; no connection from `MyLettersPage` acknowledgment back to any notification/audit-log module (outside this module's scope, but worth flagging as an integration gap since Notification/Audit-Log systems exist per project memory).

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)

- **Four distinct permission codes exist but are entirely unused — everything is gated by one.** `src/enum/modules.ts:29-34` defines `LETTER_MANAGEMENT`, `LETTER_ISSUED`, `LETTER_TEMPLATES`, `LETTER_CATEGORIES`, `LETTER_SIGNATORIES`, `LETTER_SETTINGS` as separate module codes, but a repo-wide grep shows `LETTER_CATEGORIES`, `LETTER_SIGNATORIES`, `LETTER_SETTINGS`, and `LETTER_MANAGEMENT` are never referenced outside that enum file. `CategoriesPage.tsx:39-41`, `SignatoriesPage.tsx:40-42`, `LetterSettingsPage.tsx:34`, and `TemplatesPage.tsx:43-45` all call `useModuleAccess(ModuleCode.LETTER_TEMPLATES)` regardless of which sub-feature they render. This matters because any role granted template access implicitly gets full control over categories, signatories, and org-wide numbering/default-signatory settings — the intended granular RBAC design is dead code.
- **No shared "document id → image" abstraction, so the signature-rendering gap can't be fixed locally.** As documented inline at `getInitials.ts:1-10`, resolving `signature_document_id` into a viewable image requires a signed-URL fetch pattern that doesn't exist as a reusable hook; the closest precedent (`DocumentRender` in `FeedbackDetailDrawer`) lives in an unrelated feature. This means every signatory-related surface (list card, form modal, template editor, letter preview) would need to duplicate that plumbing rather than compose it.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling, unsafe assumptions)

- **Confirmed: signature image is never uploaded-then-shown anywhere.** `SignatoryCard.tsx:31-33` renders only `getInitials(name)`; no component reads `signature.signature_document_id` for display. The upload-once-at-creation flow (`SignatoryFormModal.tsx:153` `{!isEdit && (...)}` block, lines 153-183) is the only place a signature file is ever touched client-side, and even that result is discarded visually.
- **Signature image cannot be replaced after creation.** `SignatoryFormModal.tsx:153` wraps the entire upload UI in `{!isEdit && (...)}`, so editing a signatory offers no way to change the signature file; this matches `UpdateSignatoryParams` in `api/signatory.ts:30-39`, which has no `file` field and calls `PATCH` with a plain JSON body (`updateSignatory`, line 36-39) — there is no multipart path for edits at all.
- **Archived signatories are not filtered consistently — `LetterSettingsPage` is the worst offender.** `TemplateForm.tsx:53-58` filters `signatoryOptions` to exclude `status === 'ARCHIVED'`, but `LetterSettingsPage.tsx:39-42` builds `signatoryOptions` straight from `signatoriesResponse?.data` with **no status filter at all** — an archived signatory appears as a completely normal, undistinguished option in the "Default Signatory" dropdown used to set the org-wide default for all future letters. `useSignatories()` (`api/signatory.ts:9-10`, `getSignatories`) has no status parameter, so archived rows are always included in the list response. This is exactly the kind of dropdown an admin could use to accidentally set an archived signatory as the org default.
- **Category dropdown in `TemplateForm` also filters archived items, creating an orphaned-value UX bug.** `TemplateForm.tsx:49-51` and `:53-58` both drop `ARCHIVED` categories/signatories from their `Select` options. If an existing template's `category_id`/`signatory_id` points to an item that later gets archived, re-opening that template for edit will show the `Select` with a value that matches no option in the list (effectively appears blank/unselected to the admin), rather than showing the archived item with a clear "(archived)" marker — silently misleading the admin about what's actually configured on save-less views, and risking an accidental overwrite if they resubmit the form without touching that field.
- **Dead/leftover code in `LetterSetupPage.tsx`.** Line 2 has a bare comment `// Imports removed`; lines 56-65 contain a no-op `handleTabChange` whose body is entirely comments explaining a decision not to sync the URL, and `getInitialTab()` (lines 25-27) is a function that ignores its own stated purpose ("derive initial tab from path") and just returns a constant. This is inert but signals unfinished cleanup after a refactor.

### Technical (performance, security, accessibility, test coverage)

- **No file-size/type guard beyond the `accept` attribute on signature upload.** `SignatoryFormModal.tsx:169-173` restricts the file picker to `image/png,image/jpeg` via the HTML `accept` attribute only — there's no client-side size/dimension validation before the file is attached to `FormData` in `onSubmit` (`SignatoryFormModal.tsx:109-117`), so oversized or spoofed-extension files are only ever caught server-side (or not at all until upload fails).
- **No test coverage found.** No `*.test.tsx`/`*.spec.tsx` files exist anywhere under `src/features/letter-management/` or `src/pages/letter-management/`/`src/pages/employee-letters/` — none of the archive/unarchive guards, the 3-step generate wizard, or the acknowledge flow have automated regression coverage.

## 5. Top 3 Priorities

1. **Fix the archived-signatory selectability gap in `LetterSettingsPage.tsx:39-42`** — filter out `ARCHIVED` signatories (matching `TemplateForm`'s pattern) or, better, visually mark archived items and block selection everywhere signatories are pickable; this is the one dropdown in the whole module with zero archived-state handling and it controls the org-wide default signatory used on every future letter.
2. **Either wire real signature-image rendering end-to-end or drop the upload UI** — right now signatories accept a signature upload at creation (`SignatoryFormModal.tsx`) that is stored (`signature_document_id`) but never displayed anywhere in the frontend and never rendered on the generated PDF (per backend audit); this is a fully dead feature surface that misleads admins into thinking it does something. Building the shared "document id → signed image" hook noted in `getInitials.ts` and adding a replace-on-edit path would close this in one pass.
3. **Wire up the unused granular permission codes (`LETTER_CATEGORIES`, `LETTER_SIGNATORIES`, `LETTER_SETTINGS`) or remove them** — as it stands every sub-page checks `LETTER_TEMPLATES` (`CategoriesPage.tsx:39-41`, `SignatoriesPage.tsx:40-42`, `LetterSettingsPage.tsx:34`), so the RBAC model is coarser than what was designed into the enum, and any consumer relying on the dedicated codes existing (e.g. a future platform-admin role matrix) will silently no-op.
