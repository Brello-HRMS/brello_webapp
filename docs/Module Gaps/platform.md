# Module: Platform (webapp)

## 1. Purpose & Current Usage

- `src/features/platform/` holds 12 sub-features, each with the same `api.ts` / `types.ts` / `hooks.ts` (+ optional `*FormModal.tsx`) shape: `organizations`, `plans`, `appModules`, `leads`, `designations`, `roles`, `departments`, `enterprises`, `actions`, `industryTypes`, `apps`, `planPermissions`. Together they implement CRUD/list screens for platform-wide master data: industry types, departments, designations, plans, apps/modules/actions, plan-module-permissions, enterprises, organizations, leads, and platform roles.
- `src/pages/platform/` holds one page per area (`PlatformIndustryTypePage.tsx`, `PlatformDepartmentPage.tsx`, `PlatformDesignationPage.tsx`, `PlatformPlansPage.tsx`, `PlatformAppsPage.tsx`, `PlatformModulesPage.tsx`, `PlatformActionsPage.tsx`, `PlatformPlanPermissionsPage.tsx`, `PlatformOrganizationsPage.tsx` / `PlatformOrganizationDetailPage.tsx`, `PlatformEnterprisesPage.tsx`, `PlatformLeadsPage.tsx`, `PlatformRolesPage.tsx`, `PlatformAccessPermissionsPage.tsx`, `PlatformFeedbackPage.tsx`, `PlatformDashboardPage.tsx`). Every page except `PlatformDashboardPage` and `PlatformFeedbackPage` imports directly from a matching `src/features/platform/<x>` folder (verified for all 12 sub-features — none are orphaned/dead).
- Wiring: `src/routes/platformAdminRoutes.tsx` imports every page above (plus `PlatformAuditPage` from `src/pages/audit/`) and exports `platformAdminRoutes`. `src/routes/index.tsx:80-84` mounts these at `path: '/platform'` guarded by `platformAdminLoader` (`src/routes/index.tsx:49-53`), which is a **client-side loader** that just decodes the `auth_response` cookie and checks `parsed?.data?.user?.is_platform_admin`.
- The sidebar (`src/features/sidebar/Sidebar.tsx:41-104`) renders a hardcoded `PLATFORM_ADMIN_MENU` (Dashboard, Leads, Enterprises, Organizations, Plans, Access→Roles/Permissions, Apps/Modules, Setup→Actions/Industry Types/Departments/Designations, Audit Logs, Support→Feedback/Reports) whenever `isPlatformAdminUser` (`src/utils/authUtils.ts:58-61`, same cookie-flag check) is true — i.e. gating is duplicated but uses the identical, purely client-side signal in both places.
- No dead code found inside `src/features/platform/` — every sub-feature's hooks/api are consumed by exactly one page. `PlatformDashboardPage.tsx` is a static stub (`<h1>Platform Dashboard</h1>`, no data, no feature import).
- **`platform/` vs `platformAdmin/` split**: `src/features/platformAdmin/` exists as a large, well-organized directory tree (`plans`, `leads`, `roles`, `tenants`, `defaults`, `templates`, `apps`, `billing`, `analytics`, each further split into `types/`, `components/`, `hooks/`, `api/`, `validation/` subfolders — 55 directories total) but **every one of those directories is empty (0 files)**. `grep -rln "features/platformAdmin" src` (excluding the folder itself) returns zero matches — nothing in the app imports from it, and no route references it. It reads as scaffolding for a planned refactor/rename of `platform/` that was never filled in. The currently-functioning, routed implementation is entirely `src/features/platform/` + `src/pages/platform/`, named "Platform" in the folder but wired up as `platformAdminRoutes`/`platformAdminLoader`/`isPlatformAdmin` throughout — i.e. the two names ("platform" and "platform admin") are already used interchangeably for the *same* live feature, while a second, identically-named, empty `platformAdmin` feature folder sits unused. This is very likely to confuse anyone auditing/extending "platformAdmin" in isolation, since there is no code there to find.

## 2. Intended / Ideal Usage

- A real platform administrator logs in, the backend issues a session reflecting `is_platform_admin`, and only then can they reach `/platform/*` to manage cross-tenant master data (industry types, departments, designations, plans, apps/modules/actions, enterprises, organizations, leads) and platform-level roles/permissions.
- Each sub-feature should validate input client-side (uniqueness, length), handle API errors distinctly (409 conflict vs 500, etc.), and — critically — every mutating endpoint it calls should be enforced server-side by a real platform-admin guard, so the UI gating is a convenience, not the actual security boundary.
- The `platform/` vs `platformAdmin/` naming should resolve to one canonical feature location; if `platformAdmin/` was meant to replace `platform/`, the migration should either be completed or the empty tree removed to avoid confusion.

## 3. Cross-Module Connections

**Depends on:**
- `src/lib/axios.ts` (`apiClient`) for all HTTP calls; attaches `Authorization: Bearer <token>` from the `auth_response` cookie on every request (`src/lib/axios.ts:53-60`), but does not add any platform-admin-specific header/claim — the same client used by every other feature in the app.
- `src/utils/authUtils.ts` (`isPlatformAdmin`, `isAdminApp`) and `src/routes/index.tsx` loaders for gating.
- `src/features/feedback` for the Feedback/Report pages reused inside the platform section (`PlatformFeedbackPage`).
- Backend routes: `/organizations`, `/organization-subscriptions`, `/plans`, `/app-modules`, `/leads`, `/platform-admin/designations`, `/platform-admin/departments`, `/platform-roles`, `/enterprises`, `/actions`, `/industry-types`, `/apps`, `/plan-modules`, `/plan-module-actions` — note the inconsistent naming: `departments`/`designations` go through a `/platform-admin/` prefix while `industry-types`, `plans`, `apps`, `actions`, `enterprises`, `organizations`, `leads` hit top-level, unprefixed routes, and roles use yet another prefix (`/platform-roles`).

**Depends on this:**
- Nothing outside `src/pages/platform/` and `src/routes/platformAdminRoutes.tsx` imports `src/features/platform/*` (confirmed by repo-wide grep) — it is a self-contained leaf feature area.

**Missing/expected connections — industry-type risk:**
- The industry-type management UI **does** live in this feature: `src/features/platform/industryTypes/api.ts:11` calls `${BRELLO_BASE_API}/industry-types` directly (create/update/delete, `src/features/platform/industryTypes/api.ts:14-23`), rendered by `src/pages/platform/PlatformIndustryTypePage.tsx` at route `/platform/setup/industry-types` (`src/routes/platformAdminRoutes.tsx:37`), linked from the sidebar's Setup section (`src/features/sidebar/Sidebar.tsx:88`).
- Per the backend audit (`brello_server/docs/Module Gaps/industry-type.md`), the `industry-type` controller's create/update/delete endpoints have **zero guards** — fully unauthenticated and reachable by anyone with the base API URL. The webapp only prevents *navigation* to this page via the client-side `platformAdminLoader`/`isPlatformAdmin()` cookie check (`src/routes/index.tsx:49-53`, `src/utils/authUtils.ts:58-61`). Because the cookie value is client-controlled and the actual HTTP calls carry no platform-admin-specific proof, any user (or unauthenticated caller) can call `POST/PATCH/DELETE {BASE}/industry-types` directly and mutate global industry-type master data — the "admin-only" appearance in the UI is cosmetic, not a real access boundary. This risk is systemic to the whole `platform/` feature area (every sub-feature is gated the same way), not unique to industry types — industry-types is simply the one confirmed to have zero server-side guard at all.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)
- **`platform/` vs `platformAdmin/` duplication/confusion**: `src/features/platformAdmin/` is a fully-scaffolded but entirely empty (0 files across 55 dirs) parallel feature tree that nothing imports (`grep -rln "features/platformAdmin" src` → no hits outside itself), while the live feature is `src/features/platform/` routed via files literally named `platformAdminRoutes.tsx`/`platformAdminLoader`. This split makes it unclear which tree is authoritative and risks two teams building the same feature twice, or a future dev deleting the "unused" `platform/` folder by mistake. Evidence: `src/features/platformAdmin/plans/api/` (empty dir) vs `src/features/platform/plans/api.ts` (implemented, imported by `src/pages/platform/PlatformPlansPage.tsx:13`).
- **Inconsistent backend route naming baked into the frontend**: `departments`/`designations` call `/platform-admin/...` (`src/features/platform/departments/api.ts:10`, `src/features/platform/designations/api.ts:10`) while `industry-types`, `plans`, `apps`, `actions`, `enterprises` call unprefixed top-level routes (e.g. `src/features/platform/industryTypes/api.ts:11`), and roles use `/platform-roles` (`src/features/platform/roles/api.ts:6`). This makes it hard to reason about which endpoints share a guard/prefix and increases the chance a new endpoint is added without the correct protection (as happened with industry-types).
- **`PlatformDashboardPage.tsx` is a placeholder** (`src/pages/platform/PlatformDashboardPage.tsx:1-8`) with no widgets/data, yet it's the default landing route (`/platform/dashboard`, first sidebar item) — the entry point for platform admins is effectively empty.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling, unsafe assumptions)
- **Minimal client-side validation**: `IndustryTypeFormModal` (`src/features/platform/industryTypes/IndustryTypeFormModal.tsx:69-76`) only enforces `required`, no max length or duplicate-name check against the already-loaded list, so users can submit near-duplicate names that the (unauthenticated) backend will happily persist.
- **Delete-error messaging is heuristic, not authoritative**: `useDeleteIndustryType` (`src/features/platform/industryTypes/hooks.ts:57-66`) special-cases HTTP 409 to show "in use" messaging by checking `error?.data?.statusCode === 409` rather than reading a structured error code, which is brittle if the backend response shape changes.
- No React Query `staleTime`/`gcTime` configuration or optimistic UI is applied anywhere in the 12 `hooks.ts` files reviewed (all follow the identical pattern in `industryTypes/hooks.ts`) — every mutation does a full `invalidateQueries` refetch, acceptable for low-traffic admin screens but inconsistent with patterns elsewhere in the app that use optimistic updates.

### Technical (performance, security, accessibility, test coverage)
- **SECURITY — false sense of protection**: The frontend's only gate for the entire `/platform/*` area (including industry-type CRUD) is a decoded cookie flag checked in a React Router loader (`src/routes/index.tsx:49-53`) and mirrored in the sidebar (`src/features/sidebar/Sidebar.tsx:117-133`). Neither the route loader nor `apiClient` (`src/lib/axios.ts:8-14`, `:53-60`) attaches any platform-admin-specific credential to outgoing requests — they send the same bearer token any authenticated user has. Combined with the backend's confirmed lack of guards on `industry-type` endpoints, the UI gives a materially false impression that "Industry Types" (and, by the same mechanism, every other `/platform/setup/*` and `/platform/*` screen) is admin-protected, when in practice any authenticated (or per the backend finding, even unauthenticated) caller can hit the same URLs directly.
- **Zero automated test coverage**: `find src -iname "*.test.*" -path "*platform*"` and `*.spec.*` both return no results — none of the 12 sub-features or 15 pages have unit/integration tests.
- **No accessibility affordances beyond default component library behavior** were found in the pages sampled (`PlatformIndustryTypePage.tsx`, `IndustryTypeFormModal.tsx`) — no explicit `aria-live` region for toast-driven success/error feedback, relying entirely on the shared `showToast` utility's own accessibility handling (not audited here).

## 5. Top 3 Priorities

1. **Add real server-side authorization to every `platform/`-consumed endpoint (industry-types first)** — the frontend currently provides no actual security boundary, only cosmetic UI gating, so this is an active data-integrity/security risk, not just a UX nit.
2. **Resolve the `platform/` vs `platformAdmin/` split** — either delete the empty `src/features/platformAdmin/` scaffold or make it the real migration target and retire `src/features/platform/`; leaving both around invites duplicated work and misdirected audits/fixes.
3. **Normalize backend route prefixes referenced from the frontend** (`/platform-admin/*` vs unprefixed vs `/platform-roles`) so guard coverage can be reasoned about and verified consistently across all 12 sub-features instead of endpoint-by-endpoint.
