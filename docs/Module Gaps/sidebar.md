# Module: Sidebar (webapp)

## 1. Purpose & Current Usage

- **What it does**: `src/features/sidebar/Sidebar.tsx` is the single global nav shell rendered inside `MainLayout.tsx:47` for every authenticated screen. For a normal org user it fetches the nav tree from the backend (`useSidebarMenu` → `GET {BASE}/menu`, `src/features/sidebar/api/sidebar.ts:6-8`) and maps the response into `MenuItem[]` (`Sidebar.tsx:132-155`). For a platform-admin user (`isPlatformAdmin()`) it skips the API entirely (`useSidebarMenu({ enabled: !isPlatformAdminUser })`, `Sidebar.tsx:122`) and renders a fully hardcoded `PLATFORM_ADMIN_MENU` array (`Sidebar.tsx:41-106`).
- Collapse/expand is local `useState` (`isCollapsed` prop from `MainLayout`), with `NavItem.tsx` driving an inline expand (`ExpandedSubMenu`) when open and a hover-triggered flyout (`CollapsedHoverSubMenu`, portal to `document.body`) when the rail is collapsed.
- During incomplete org setup, `isMenuItemFree`/`isSetupIncomplete` (`Sidebar.tsx:35-39, 126-155`) locks any menu item whose path(s) aren't in `SETUP_FREE_PATHS` (`src/components/common/SetupGuard/SetupGuard.tsx:11-22`), showing a lock icon instead of a chevron (`NavItem.tsx:78-79`).
- Icons come from `iconMapper.ts`, translating the backend's `icon` string to a `lucide-react` component, falling back to a generic `Circle` if unmapped (`iconMapper.ts:53-56`).
- **Who uses it**: it's global — every admin-app and platform-app route renders inside `MainLayout`, so this is structurally the busiest component in the frontend.
- **Dead/unused parts**:
  - `src/features/sidebar/components/OrgBanner/OrgBanner.tsx` (+ its `.scss`) is never imported anywhere in the app (`grep -rn "OrgBanner" src` only matches the file itself) — a whole org-logo/name header component that duplicates what `Sidebar.tsx`'s own header already does inline (`Sidebar.tsx:177-194`).
  - The `actions` field is read off the API response and threaded onto every `MenuItem`/`SubMenuItem` (`Sidebar.tsx:139,146`), but no renderer (`NavItem.tsx`, `ExpandedSubMenu.tsx`, `CollapsedHoverSubMenu.tsx`) ever reads `item.actions` — it's dead data carried through three component layers.

## 2. Intended / Ideal Usage

- The nav should be a pure, real-time reflection of what the logged-in user can actually do: an item appears if and only if the guarded route behind it will render (not a 403), for both the org-admin app and the platform app, through one consistent permission-resolution mechanism.
- Icons, labels, and paths should be driven entirely by backend module metadata, with no silent gaps between what's seeded and what the frontend knows how to render.
- Nav should be fully keyboard-operable (open/close submenus, activate items) and expose proper ARIA semantics for assistive tech, matching that it's the primary navigation surface of the app.

## 3. Cross-Module Connections

- **Depends on**:
  - Backend `GET /menu` and `GET /menu/permissions` (`brello_server/src/modules/rbac/controllers/menu.controller.ts`), both built from `PermissionResolverService.resolve()` (`brello_server/src/modules/rbac/services/permission-resolver.service.ts`).
  - `useOrgSetupStatus` / `SetupGuard` for the setup-incomplete lock behavior.
  - `useSearchStore` for the Cmd+K search modal trigger.
  - `authUtils.isPlatformAdmin`/`isAdminApp` to branch between the RBAC-driven menu and the hardcoded platform menu.
- **Depends on this**: every page in the app, structurally — `MainLayout.tsx` mounts `Sidebar` once for the whole authenticated shell.
- **Verifying the two findings flagged going in**:
  - `HIDDEN_SIDEBAR_PATHS` **does not exist** anywhere in this codebase today — confirmed via `grep -rn "HIDDEN_SIDEBAR_PATHS"` across `src/` (no hits) and `git log --all -p -S "HIDDEN_SIDEBAR_PATHS"` (no hits in any commit on any local branch). Whatever surfaced this earlier is stale relative to the current tree.
  - The `/letter-management/${tabId}` vs `/organisation/letter-management/...` **path-mismatch bug is also not present**. Routes today are flat: `letter-management/issued-letters` and `letter-management/setup` (`src/routes/adminRoutes.tsx:110-124`), not nested under `organisation/`. `LetterSetupPage.tsx` no longer navigates on tab switch at all — `handleTabChange` (`LetterSetupPage.tsx:57-65`) deliberately just sets local state, with an inline comment explaining this was done specifically so tab switching doesn't fight the sidebar's route-based active-highlighting. This was reworked in commit `3b4f012` ("refactor: restructure letter management module...").
  - Instead, a bigger, currently-real gap exists in the same area (see 4.Coding below): the RBAC module codes the letter-management routes depend on (`LETTER_ISSUED`, `LETTER_TEMPLATES`) have no backing rows in the backend's module seed data at all, so this isn't a matter of the sidebar *hiding* letter-management items — it can never *show* them for anyone, and the routes 403 unconditionally.
- **Other missing/expected connection**: the platform-admin branch of `Sidebar.tsx` never calls `/menu` and is not filtered by any permission model, even though the backend has its own `platform-role.controller.ts` and the platform app ships `Access > Roles` / `Access > Permissions` pages implying platform admins are meant to have differentiated access.

## 4. Gaps

### Structural

1. **Two unrelated code paths implement "the nav"** — one is backend-driven (`useSidebarMenu` → `/menu`) for the org-admin app, the other is a fully static `PLATFORM_ADMIN_MENU` array (`Sidebar.tsx:41-106`) for the platform app, selected by a single boolean flag (`is_platform_admin`, `authUtils.ts:58-61`). This isn't `HIDDEN_SIDEBAR_PATHS`-style path exclusion (that pattern isn't present), but it is the same kind of special-casing risk: as platform RBAC (`platform-role.controller.ts`, `/platform/access/roles`) matures, this hardcoded menu will silently drift out of sync with what a given platform admin is actually allowed to do — every platform-admin-flagged user sees the identical full menu (Leads, Enterprises, Organisations, Plans, Access, App & Modules, Setup, Audit Logs, Support) regardless of role. Matters because it's a total bypass of the RBAC surface the rest of the app relies on for exactly this purpose.
2. **`/menu` and `/menu/permissions` share one inclusion rule that's too loose for the guard that consumes it.** `PermissionResolverService.buildModuleResult` (`permission-resolver.service.ts:300-335`) includes a module in the resolved tree — and therefore in the sidebar and in `checkModuleAccess` — as soon as it has *any* granted action (`actions.size > 0`), not specifically `view`. But `RequireAccess`/`useModuleAccess` on the frontend (`src/hooks/useModuleAccess.ts:25-43`, `src/components/common/RequireAccess/RequireAccess.tsx:29,39`) gate the actual route on `hasViewAccess` specifically. Verified (via code inspection of `src/pages/access/PermissionsPage.tsx:96-129` and `brello_server/src/modules/app-module/services/module-access.service.ts:278-398` / `dto/module-access.dto.ts:42-61`) that nothing anywhere enforces "view implies/is implied by other actions" — an admin can save a role with `edit=true, view=false` on a module. Net effect: a role like that gets the item rendered in the sidebar, but clicking it always lands on `ForbiddenPage`. This is the structural root cause behind "could the sidebar show items the user can't actually access" — yes, and it's traceable to a real, reachable configuration, not a hypothetical.

### Coding

1. **Letter Management module codes have no backing RBAC data at all.** `RequireAccess module={ModuleCode.LETTER_ISSUED}` / `ModuleCode.LETTER_TEMPLATES` (`adminRoutes.tsx:110-124`) and `LetterSetupPage.tsx:32` all key off codes that never appear in any backend seed or migration — `grep -rn "code:\s*['\"]LETTER" brello_server/src` returns nothing, and `brello_server/src/seeds/seed-brello-v2-base.ts` only seeds unrelated legacy codes (`HR_LETTERS`, `HR_OFFER_LETTERS`, `HR_INTERNAL_LETTERS`). Since `PermissionResolverService.resolve()` (`permission-resolver.service.ts:106-112`) only ever considers `AppModule` rows that exist in the database, it can never produce `LETTER_ISSUED`/`LETTER_TEMPLATES` for any role. Consequence: the "Issued Letters"/"Letter Setup" sidebar entries can never render for *any* user, and the routes 403 unconditionally even for org admins — the feature is currently orphaned from the RBAC tree entirely, not selectively hidden.
2. **`iconMapper.ts`'s icon map is far behind the backend's seeded icon names.** The map only defines 22 names (`iconMapper.ts:28-51`), but `seed-brello-v2-base.ts` uses 18+ distinct names not present in it at all — e.g. `Settings`, `User`, `Calendar`, `FileText`, `Wallet`, `PartyPopper`, `List`, `PlayCircle`, `Building`, `FileSignature`, `Network`, `Award`, `Lock`, `Key`, `CreditCard`, `Tag`, `History`, `ClipboardList`. Every one silently falls back to a plain `Circle` (`iconMapper.ts:53-56`) with no warning logged — so roughly half of the real seeded modules (Departments, Designations, Leave Requests, Payslips, Payroll Listing/Process, Clients, HR Letters, Permissions, Billing Plan, Payment History, etc.) render a generic dot instead of their intended icon in production today.
3. **`OrgBanner.tsx` is dead code** — a full component + stylesheet under `src/features/sidebar/components/OrgBanner/` that is never imported anywhere (confirmed by repo-wide grep). It should either be wired in or deleted.
4. **The `actions` field is plumbed through but never consumed** (`Sidebar.tsx:139,146` → `MenuItem.actions`/`SubMenuItem.actions` in `sidebarConfig.ts`/`types/sidebarType.ts`) — no component reads it, so it's unused data flowing through the whole render pipeline.

### Technical

1. **Zero test coverage** — there isn't a single `*.test.*`/`*.spec.*` file anywhere under `src/features/sidebar`, and in fact none in the whole `brello_webapp` repo (`find . -iname "*.test.*" -o -iname "*.spec.*"` → 0 results). No coverage exists for the menu-tree mapping, the setup-lock logic, or the platform/org branching — all of which are pure-enough logic to be cheaply unit tested.
2. **No keyboard accessibility on nav items.** `NavItem.tsx:67-70`'s clickable row is a plain `<div onClick={handleClick}>` with no `role="button"`, no `tabIndex`, no `onKeyDown` handling for Enter/Space, and no `aria-expanded`/`aria-haspopup` for items with children. The only `aria-label` in the entire feature is on the search button (`Sidebar.tsx:198`). A keyboard-only user cannot open, traverse, or activate any part of the primary navigation.
3. **`CollapsedHoverSubMenu` is mouse-only.** When the rail is collapsed, child items are exposed exclusively through a `mouseenter`-triggered portal flyout (`NavItem.tsx:49-56`, `CollapsedHoverSubMenu.tsx`) with no keyboard or focus-triggered equivalent, so collapsed-mode submenus are entirely unreachable without a mouse.

## 5. Top 3 Priorities

1. **Seed the Letter Management RBAC module rows (`LETTER_ISSUED`, `LETTER_TEMPLATES`, etc.) in the backend.** This is the single biggest gap: the feature is currently invisible in the sidebar and unconditionally forbidden via direct URL for every user, org admins included, because the permission resolver has no module rows to key off — not a filtering choice, a missing-data bug.
2. **Close the view-vs-any-action gap between menu building and route guarding** (`permission-resolver.service.ts:300-335` vs `useModuleAccess.ts`), and/or enforce a "view is implied by any granted action" rule in the permissions-save path (`PermissionsPage.tsx`, `module-access.service.ts`) — otherwise the sidebar can and will show items that 403 on click for any role missing explicit `view`.
3. **Unify the platform-admin nav with the same RBAC-driven mechanism as the org-admin nav**, or explicitly filter `PLATFORM_ADMIN_MENU` against the platform role's actual permissions — right now every platform-admin-flagged user sees an identical, unfiltered full menu regardless of their assigned role.
