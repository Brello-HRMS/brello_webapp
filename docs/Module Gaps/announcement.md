# Module: Announcement (webapp)

## 1. Purpose & Current Usage

- **Feature root**: `src/features/announcement/` — API client, hooks, types, zod validation, columns, and two components (`CreateAnnouncementModal`, `AnnouncementDetailDrawer`).
- **Pages**: `src/pages/announcement/AnnouncementPage.tsx` (admin list/manage view) and `src/pages/announcement/EmployeeAnnouncementPage.tsx` (employee read-only view).
- **API layer** (`src/features/announcement/api/announcementApi.ts:1-85`): thin axios wrappers calling `brello_server`'s announcement module — `createAnnouncement`, `getAnnouncements`, `getAnnouncement`, `updateAnnouncement`, `deleteAnnouncement`, `publishAnnouncement`, `archiveAnnouncement` (admin, base `${BRELLO_BASE_API}/announcements`), plus `getEmployeeAnnouncements`/`markAnnouncementRead` (employee, base `${BRELLO_BASE_API}/employee/announcements`).
- **Hooks** (`src/features/announcement/hooks/useAnnouncement.ts:1-144`): React Query wrappers around the API — `useAnnouncements`, `useCreateAnnouncement`, `useUpdateAnnouncement`, `useDeleteAnnouncement`, `usePublishAnnouncement`, `useArchiveAnnouncement`, `useEmployeeAnnouncements`, `useMarkAnnouncementRead`. All admin mutations invalidate `['announcements','admin']` and toast on success/error.
- **Admin usage** — `src/pages/announcement/AnnouncementPage.tsx:1-167`: lists announcements in a `DataTable` (search, manual pagination), opens `CreateAnnouncementModal` for create/edit, and drives publish/archive/delete via `WarningModal` confirmation dialogs (lines 136-161).
- **Employee usage** — `src/pages/announcement/EmployeeAnnouncementPage.tsx:1-63`: lists the employee's own announcements, opens `AnnouncementDetailDrawer` on row click, which auto-calls `markAnnouncementRead` on open (`AnnouncementDetailDrawer.tsx:45-49`).
- **Routing**: `src/routes/adminRoutes.tsx:288-303` wires `/announcements` → redirect to `/announcements/list` (admin app) gated by `<RequireAccess module={ModuleCode.ANNOUNCEMENT}>`; `src/routes/employeeRoutes.tsx:9` wires `/announcements/me` → `EmployeeAnnouncementPage` with **no** `RequireAccess`/module gate (relies on whatever wraps `employeeRoutes` overall, unlike the admin route which gates per-page).
- **Dead/unused parts**: the `AnnouncementAttachment` type (`announcementTypes.ts:39-45`) and `attachments` field on `Announcement`/`CreateAnnouncementPayload` are read-only in practice — `AnnouncementDetailDrawer.tsx:75-101` renders them, but `CreateAnnouncementModal.tsx` never includes an attachments field in its form, default values, `onSubmit` payload, or `reset()` call, so no admin can ever attach a file through the UI. The `department_ids`/`location_ids`/`employee_ids` audience-targeting fields are likewise write-dead (see §4).

## 2. Intended / Ideal Usage

- Admin composes a title + rich content, picks a priority, chooses an audience (all company, specific departments/locations/employees), optionally attaches files, decides push/email delivery, and either publishes instantly or schedules for a future time.
- If scheduled, the announcement should sit in `SCHEDULED` status until a backend job publishes it at `scheduled_at`, then employees in the target audience see it and can mark it read.
- The admin table should allow filtering by status/priority (types support it via `AdminAnnouncementQuery.status`/`priority`, `announcementApi.ts:29-35`) and show real per-audience read analytics (`AnnouncementAnalytics`, `announcementTypes.ts:33-37`).
- Employees should see only announcements actually targeted at them, in a safe rendered format (no ability to inject script via crafted content).

## 3. Cross-Module Connections

- **Depends on**:
  - `brello_server` announcement module REST endpoints (`/announcements`, `/announcements/:id`, `/announcements/:id/publish`, `/announcements/:id/archive`, `/employee/announcements`, `/employee/announcements/:id/read`) — see `announcementApi.ts:14-15`.
  - Shared UI kit: `Dialog`, `Button`, `Select`, `Input`, `WarningModal`, `DataTable`, `PageHeader`, `ListControls` (`src/components/common/*`).
  - `MarkdownEditor` (`src/components/common/MarkdownEditor/MarkdownEditor.tsx`), a thin wrapper around the third-party `md-editor-rt` library, used for both authoring and read-only rendering.
  - `RequireAccess`/`ModuleCode.ANNOUNCEMENT` RBAC gate (frontend-only) and `isAdminApp()` helper for the admin/employee route split.
- **Depended on by**:
  - `AnnouncementPage` (admin nav item) and `EmployeeAnnouncementPage` (employee nav item), both reachable only through the routes above — no other feature imports from `features/announcement/`.
- **Missing/expected connections**:
  - **No UI warning that "Schedule for later" silently won't fire.** `CreateAnnouncementModal.tsx:37-40,223-231` lets the admin pick `AnnouncementPublishType.SCHEDULED` and a future `scheduled_at` with only a "must be a future date" validation message (`announcementSchema.ts:23-31`) — there is no messaging anywhere in the modal, the admin list (`adminAnnouncementColumns.tsx:29-34` just shows a `◷ Scheduled` badge), or the confirm dialogs indicating that the backend has no cron consuming `findDueScheduled` (per the server-side audit). The UI presents scheduling as a fully working feature when it is a dead end that silently never publishes.
  - No audience-targeting UI is wired to the `DEPARTMENTS`/`LOCATIONS`/`EMPLOYEES` audience types the schema/types fully support (see §4 Structural) — so the cross-module connection to department/location/employee-picker components that should exist simply doesn't.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)

- **Audience targeting is exposed but not implemented in the form.** `CreateAnnouncementModal.tsx:233-246` renders only the `audience_type` `Select`; there is no follow-up multi-select for `department_ids`, `location_ids`, or `employee_ids` anywhere in the JSX (confirmed by grep — those fields only appear in `DEFAULT_VALUES`, the `reset()` prefill, and the submit payload, `CreateAnnouncementModal.tsx:56-58,95-97,116-118`). Picking "Specific departments/locations/employees" produces a payload with empty arrays for every targeting field, i.e. the announcement is created with an audience type that doesn't actually target anyone — a broken feature masquerading as available in the dropdown. This matters because admins can silently create no-op or empty-audience announcements believing they've scoped them.
- **Attachments are read-only wiring, not a real feature.** `AnnouncementAttachment`/`attachments` are modeled end-to-end in types (`announcementTypes.ts:39-45,60,75,103`) and rendered in `AnnouncementDetailDrawer.tsx:75-101`, but `CreateAnnouncementModal.tsx` has no file input, no upload call, and never includes `attachments` in its submitted payload — so the read path exists for a write path that doesn't. This is incomplete-feature debt that should either be finished or the display code/type surface removed.
- **Field misnamed relative to its actual content type.** The form field and API payload are named `description_html` throughout (`announcementTypes.ts:50,71,96,121`), and the zod schema/label call it "Description" — but the editor bound to it is `MarkdownEditor` (`CreateAnnouncementModal.tsx:171-185`), which is a Markdown editor (`md-editor-rt`), not an HTML/rich-text editor. The value stored and sent to the backend as `description_html` is raw Markdown source, not HTML, despite the name and despite the backend's `description_html` column presumably expecting/treating it as HTML. This is a naming/contract mismatch between frontend and backend that will confuse anyone maintaining either side, and is the root cause of the XSS-adjacent gap below.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling, unsafe `dangerouslySetInnerHTML` usage)

- **No client-side sanitization is configured for the Markdown/HTML preview pipeline.** `MarkdownEditor.tsx:61-99` invokes `MdEditor`/`MdPreview` from `md-editor-rt` without passing the library's `sanitize` prop; the library's own type definitions (`node_modules/md-editor-rt/lib/types/index.d.ts:235-239`) explicitly recommend passing DOMPurify or `sanitize-html` because it does not sanitize by default. Since Markdown supports raw inline HTML, and `AnnouncementDetailDrawer.tsx:71` renders untrusted `announcement.description_html` straight into `MdPreview` with no sanitize function, any admin (or anyone who can hit the create/update endpoint given the backend's total lack of RBAC per the server-side audit) can embed `<script>`/`<img onerror>` payloads that execute in every employee's browser when they open the announcement. This directly compounds the backend's missing HTML sanitization into an actual client-side XSS execution point.
- **No error boundary/empty-state handling for query errors.** `useAnnouncements`/`useEmployeeAnnouncements` (`useAnnouncement.ts:16-28,118-130`) surface `error: query.error` but neither `AnnouncementPage.tsx` nor `EmployeeAnnouncementPage.tsx` reads or displays it — a failed list fetch renders an empty table with no feedback to the user (only `isLoading` is checked, e.g. `AnnouncementPage.tsx:115-129`).
- **Toggle buttons for push/email notifications have no accessible label or role.** `CreateAnnouncementModal.tsx:253-263,271-281` renders bare `<button>` elements toggled by CSS class (`styles.active`) with no `aria-pressed`, `aria-label`, or `role="switch"` — a screen reader announces them as unlabeled buttons.

### Technical (performance, security, accessibility, test coverage)

- **Security (XSS)**: as above — unsanitized Markdown-to-HTML rendering of admin-authored (and, given zero backend RBAC, potentially attacker-authored) content in `AnnouncementDetailDrawer.tsx:71` is the standout finding; see Coding section for full evidence.
- **No accessibility labeling** on interactive toggle controls (`CreateAnnouncementModal.tsx:253-281`), noted above.
- **Zero test coverage**: no `*.test.*`/`*.spec.*` files exist anywhere under `src/features/announcement/` or `src/pages/announcement/` — none of the API layer, hooks, validation schema, or components have any automated tests.
- **No frontend RBAC gate on the employee announcements route**: `src/routes/employeeRoutes.tsx:9` wires `announcements/me` with no `RequireAccess` wrapper, inconsistent with the admin route's per-page `RequireAccess module={ModuleCode.ANNOUNCEMENT}` gate (`adminRoutes.tsx:296-303`); if the employee route tree isn't uniformly gated elsewhere, this is an inconsistency worth confirming against the router's parent-level guards.

## 5. Top 3 Priorities

1. **Sanitize rendered announcement content before display** (`AnnouncementDetailDrawer.tsx:71`, `MarkdownEditor.tsx:61-99`) — pass a `sanitize` (DOMPurify) function into `MdEditor`/`MdPreview`. This is a live stored-XSS vector every employee opening an announcement is exposed to, and it compounds the backend's own missing sanitization — fixing it client-side is a cheap, high-value mitigation regardless of what the backend does.
2. **Tell the admin that "Schedule for later" doesn't work**, or remove the option until the backend cron exists — currently `CreateAnnouncementModal.tsx:37-40,223-231` presents scheduling as a normal, working feature with no indication it silently never publishes, which is a broken promise to admins who will believe a scheduled announcement went out.
3. **Either implement or remove the department/location/employee audience-targeting UI** (`CreateAnnouncementModal.tsx:233-246` vs. the unused `department_ids`/`location_ids`/`employee_ids` fields) — right now selecting a targeted audience type produces an announcement with an empty target list, silently defeating the admin's intent.
