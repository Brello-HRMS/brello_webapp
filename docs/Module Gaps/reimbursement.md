# Module: Reimbursement (webapp)

## 1. Purpose & Current Usage

- Lets employees submit expense reimbursement requests with receipt attachments, edit/delete their own pending requests, and track status. Lets admins list all org requests, approve/reject with a reason, and mark them paid.
- Employee surface: `src/pages/reimbursement/EmployeeReimbursementPage.tsx` (route `reimbursement/me`, registered in `src/routes/employeeRoutes.tsx:8`, no `RequireAccess` gate) renders a `DataTable` via `employeeReimbursementColumns` (`src/features/reimbursement/columns/employeeReimbursementColumns.tsx`) and opens `AddReimbursementModal` (`src/features/reimbursement/components/AddReimbursementModal/AddReimbursementModal.tsx`) for both create and edit.
- Admin surface: `src/pages/reimbursement/ReimbursementPage.tsx` (route `reimbursement/list`, gated by `RequireAccess module={ModuleCode.REIMBURSEMENT}` in `src/routes/adminRoutes.tsx:280-286`) renders `adminReimbursementColumns` and opens `EditReimbursementDrawer` (`src/features/reimbursement/components/EditReimbursementDrawer/EditReimbursementDrawer.tsx`) for status changes and marking paid.
- Data layer: `src/features/reimbursement/api/reimbursementApi.ts` (plain axios wrappers around `/reimbursements` and `/admin/reimbursements`), consumed by `src/features/reimbursement/hooks/useReimbursement.ts` (employee: create/update/delete/list, React Query + toast) and `useAdminReimbursement.ts` (admin: list/update-status/mark-paid).
- File upload: `AddReimbursementModal.tsx:109-119` calls the generic document API (`src/api/documents.ts`: `uploadDocumentUrl` then `uploadDocumentData`) with `folderType: 'REIMBURSEMENT_DOCUMENT'`, collecting a client-side list of `{ documentId, name, size }` that is later sent as `document_ids` / `add_document_ids` / `remove_document_ids`.
- Dead/unused: no test files exist anywhere under `src/features/reimbursement` or `src/pages/reimbursement` (confirmed via search). `EmployeeReimbursementQuery`/`AdminReimbursementQuery` (`reimbursementTypes.ts:79-91`) define `status`, `is_paid`, `from_date`, `to_date`, `sort` filters that neither page ever populates — `ReimbursementPage.tsx:58-60` explicitly sets `showFilters={false} showSort={false}` on `ListControls`, and the employee page doesn't render `ListControls` at all.

## 2. Intended / Ideal Usage

- Employee fills the form, uploads receipt(s) (validated client-side to PDF/JPG/PNG ≤10MB), submits; request appears as Pending; employee can edit/delete only while Pending. Admin reviews the queue, approves or rejects (with a reason employees can see), then marks paid once processed. Both sides should be able to see current status and, on rejection, the reason — ideally backed by a notification when status changes.

## 3. Cross-Module Connections

- **Depends on**: generic document upload service (`src/api/documents.ts`) for receipt storage; `ModuleCode.REIMBURSEMENT` access-control gate (admin route only); shared `DataTable`/`Dialog`/`Select` UI kit.
- **Depends on this**: nothing else in the frontend references reimbursement data (no dashboard widgets, no audit-log deep link beyond the generic `AuditLogModule.REIMBURSEMENT` badge in `src/features/audit/components/AuditModuleBadge/index.tsx:22`).
- **Missing/expected connections**:
  - No notification integration anywhere in this feature (confirmed: zero matches for "notif"/"Notification" in the whole folder) — matches the backend finding that submit/approve/reject/mark-paid are silent server-side. The frontend does nothing to compensate (no polling banner, no "pending review" indicator elsewhere).
  - `EditReimbursementDrawer.tsx:227-229` renders literal copy **"This comment will be visible to the employee"** next to the Rejection Reason textarea — but there is no employee-facing UI that ever reads or displays `rejection_reason`. `employeeReimbursementColumns.tsx` only renders a status badge (`renderStatusBadge`, lines 16-32, 79); the only edit surface available to employees, `AddReimbursementModal`, never references `rejection_reason` at all. So the claimed visibility is false in the current UI — an employee whose request is rejected has no in-app way to see why.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)

- No employee-facing detail/read view: `Reimbursement` carries `rejection_reason`, `approved_by`, `approved_at`, `paid_at` (`reimbursementTypes.ts:32-37`), but the only employee-side modal (`AddReimbursementModal`) is an edit form with no read-only status/history section — matters because the data model already anticipates showing this to employees but no component exists to do it.
- File-upload orchestration (create signed URL, PUT file, track per-file loading/error state) is written inline inside `AddReimbursementModal.tsx:91-129` with no reusable hook, unlike the query/mutation hooks used elsewhere in the feature — matters because retry/cancel/progress logic can't be reused if another module needs receipt-style uploads, and error handling here is a single shared string (`attachmentError`) rather than per-file state.
- Filter/sort query params defined in the types (`reimbursementTypes.ts:79-91`) are entirely unused by both pages (`ReimbursementPage.tsx:58-60` disables them, `EmployeeReimbursementPage` has no filter UI) — matters because it signals a mismatch between the API contract and the shipped UI, and admins reviewing "company-wide expense requests" have no way to filter by status or date range.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling, unsafe assumptions)

- **Submit button appears permanently disabled after any input**: `AddReimbursementModal.tsx:187` — `disabled={isSaving || uploadingCount > 0 || isDirty}`. Because `title`/`expense_date`/`amount` are required fields starting empty, `isDirty` flips to `true` the moment the user types anything, and the button stays disabled from then on (there's no `<form onSubmit>` fallback — the Dialog's `actions` are plain buttons, see `Dialog.tsx`). This looks like an inverted condition (probably intended `!isDirty` to block no-op "Save Changes" clicks) and as written blocks the primary create/edit action for both new submissions and edits.
- **Silent no-op when reverting status to Pending**: `EditReimbursementDrawer.tsx:75-90` — the status `<Select>` always offers `Pending` (`STATUS_OPTIONS`, lines 28-32) even for an already Approved/Rejected item, but `onSubmit` only calls `updateStatus` when the new status is `APPROVED` or `REJECTED` (line 77). Choosing "Pending" and clicking Save closes the drawer with no API call and no toast, giving the admin no feedback that nothing happened.
- **"Mark as Paid" toggle isn't gated by approval status**: `EditReimbursementDrawer.tsx:233-253` — the toggle is only disabled when `reimbursement.is_paid` is already `true`; it can be flipped on for a Pending or Rejected request with no client-side check that the request is Approved first, so `markPaid` (`useAdminReimbursement.ts:46-64`) can be invoked against unapproved requests, relying entirely on the backend to reject it (with no dedicated error messaging for that case).
- **Hardcoded currency assumption**: `AddReimbursementModal.tsx:218` hardcodes the label `"Amount (₹)"`, and both column files use `formatINR` unconditionally, even though `Reimbursement.currency` (`reimbursementTypes.ts:30`) is a real field returned by the API — it's fetched but never read anywhere in the feature.

### Technical (performance, security, accessibility, test coverage)

- **Receipt document_ids are trusted client input with no binding to the upload session**: `AddReimbursementModal.tsx:106-126` uploads a file, gets back a `documentId` from `uploadDocumentUrl`, and stores it in local component state; `onSubmit` (lines 135-167) then sends that array verbatim as `document_ids` / `add_document_ids` in a plain JSON POST/PUT (`reimbursementApi.ts:21-26, 37-43`). Nothing in the request ties a `document_id` back to the upload call that produced it — a user with devtools/API access can replay the create/update request with an arbitrary `document_id` string (e.g. one seen in another org's/employee's attachment URL) and the frontend provides no client-side signature/ownership check to prevent it, which lines up exactly with the backend-confirmed IDOR (server never validates `document_ids` against tenant/ownership either).
- **Search silently misses off-page results**: `ReimbursementPage.tsx:29-38` filters `items` (only the current server-paginated page, since `manualPagination` is used) client-side by employee name/code/title, while `pageCount` (line 45) is still derived from the unfiltered `meta.total`. Searching for a match that isn't on the currently loaded page renders an empty table while the pagination control still claims multiple pages of results.
- **Zero automated test coverage**: no `*.test.*`/`*.spec.*` files exist anywhere under `src/features/reimbursement` or `src/pages/reimbursement`, for a feature that handles money amounts, approval workflows, and file uploads.

## 5. Top 3 Priorities

1. **Fix the inverted `isDirty` condition in `AddReimbursementModal.tsx:187`** — as written it appears to make the Submit/Save button unusable as soon as a user types into any required field, which would block the entire create/edit flow for this feature.
2. **Close the document_ids trust gap on the create/update payload** (`AddReimbursementModal.tsx:106-167`, `reimbursementApi.ts:21-26,37-43`) — the frontend has no mechanism preventing an attacker from substituting an arbitrary `document_id` into the request, compounding the backend IDOR already identified; fixing this needs coordinated frontend+backend work (e.g. server-side ownership check plus a scoped upload token).
3. **Reconcile the "visible to the employee" rejection-reason claim with reality** (`EditReimbursementDrawer.tsx:227-229` vs. the missing employee-facing display of `rejection_reason`) and pair it with the already-known absence of notifications — right now a rejected employee has no in-app way to learn their request was rejected or why.
