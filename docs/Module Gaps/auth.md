# Module: Auth (webapp)

## 1. Purpose & Current Usage

`src/features/auth/` implements the client side of registration/login: a lead-registration form, OTP-only login (no password login screen), company/workspace setup, a welcome screen, and the shared cookie-backed session used by every route guard in the app.

- **API layer** (`src/features/auth/api/`): `auth.ts` (raw `apiClient` calls), `authType.ts` (request/response types), and one `useMutation`/`useQuery` hook per endpoint — `useLogin.ts` (`useLogin`, `useLoginWithOTP`, `useVerifyLoginOtp`), `useVerifyOtp.ts`, `useResendOtp.ts`, `useRegister.ts`, `useSetupCompany.ts`, `useLogout.ts`, `useAvailableApps.ts`, `useIndustryTypes.ts`.
- **Components** (`src/features/auth/components/`): `Login/Login.tsx` (email-only "Send OTP" form, no password field), `OtpForm/OtpForm.tsx` (6-digit OTP, shared by login and lead-verification flows), `Register/RegisterForm.tsx` (lead signup), `Lead/LeadForm.tsx` (company/workspace setup after signup), `Welcome/WelcomeScreen.tsx`, `AuthLayout/AuthLayout.tsx`, `AuthFormWrapper/AuthFormWrapper.tsx`.
- **Session mechanics** live outside this folder: `src/lib/axios.ts` (token attach + 401/refresh interceptor), `src/utils/cookieUtils.ts` (raw `document.cookie` get/set/remove), `src/utils/authUtils.ts` (`getAuthResponse`/`getAuthUser`/`isPlatformAdmin`/etc., all derived from the same cookie), `src/routes/index.tsx` and `src/routes/adminRoutes.tsx` (route loaders that gate access).
- **Used by**: `Login.tsx` (`useLoginWithOTP`, `src/features/auth/components/Login/Login.tsx:10,34-45`) → `OtpForm.tsx` (`useVerifyLoginOtp`, `src/features/auth/components/OtpForm/OtpForm.tsx:8,105-121`) is the only real login path exercised in the UI. `RegisterForm.tsx` → `OtpForm.tsx` (`useVerifyOtp`, non-login branch, `OtpForm.tsx:122-131`) → `/auth/login` is the signup path. `LeadForm.tsx` (`useSetupCompany`, `src/features/auth/components/Lead/LeadForm.tsx:37-47`) runs after first login when `setup_required` is true. `useLogout` (`src/features/auth/api/useLogout.ts`) is presumably wired from a header/menu component (not found under `src/features/auth/`, confirmed not called from any auth component itself).
- **Dead/unused code**: `useLogin` (password-based login, `src/features/auth/api/useLogin.ts:12-17`, and `login()` in `auth.ts:35-37`) is defined end-to-end — types, API call, hook — but is never invoked by any component; there is no password-login UI anywhere in the app (`Login.tsx` only calls `useLoginWithOTP`). The `README.md` (`src/features/auth/README.md:9-11`) documents `hooks/`, `types/`, and `routes/` subfolders that do not exist in the actual directory tree — stale documentation.

## 2. Intended / Ideal Usage

Correct frontend auth handling would: keep the access token out of any JS-readable storage (in-memory or a `HttpOnly` cookie set by the server, never `document.cookie` written by client code); expose auth state through a single `AuthContext`/`useAuth` hook rather than ad-hoc cookie parsing scattered across files; proactively handle token expiry using the server-reported `expires_in` (e.g. a refresh timer) instead of only reacting to a 401; fully reset all client state on logout — clear the session cookie **and** the React Query cache (`queryClient.clear()`) so a second user on a shared device never sees a stale screen or cached API response from the previous session; and give OTP entry baseline brute-force friction (e.g., disabling the input/showing a hard stop after N failed attempts) as defense-in-depth on top of server-side rate limiting.

## 3. Cross-Module Connections

- **Depends on**: `src/lib/axios.ts` (`apiClient`, token attach/refresh interceptor), `src/utils/cookieUtils.ts` (cookie read/write), `src/features/ToastFeature/ShowToast` (`showToast`), shared UI (`Input`, `Button`, `PhoneInput`, `Select`), `src/lib/react-query.ts` (module-singleton `queryClient`).
- **Depended on by**: virtually every other route/feature. Mechanism: `src/routes/index.tsx:16-27,42-60` and `src/routes/adminRoutes.tsx:274-276,291-293` gate every non-auth route via `createBrowserRouter` loaders that call `getCookie('auth_response')` directly (no shared `AuthContext`); `src/lib/axios.ts:15-29` reads the same cookie to attach `Authorization: Bearer <token>` to every API call; `src/utils/authUtils.ts` is imported by feature code (e.g. `src/components/layout/Header/AppSwitcher.tsx:5,25`) to read `enterprise_id`/`organization_id`/`is_platform_admin` for authorization decisions app-wide.
- **Missing/expected connections**: there is no `AuthContext`/`AuthProvider` despite `src/app/provider.tsx:17` explicitly commenting `{/* Add global providers here (e.g. AuthProvider) */}` — auth-derived state (`isAuthenticated`, `isPlatformAdmin`) is instead independently re-implemented in `src/routes/index.tsx:16-27` and duplicated (differently) in `src/utils/authUtils.ts`, so there are two separate sources of truth for the same cookie payload. `useLogout` never touches `queryClient` — no connection from logout to the React Query cache at all.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)
- **No `AuthContext`/`AuthProvider` despite being planned.** `src/app/provider.tsx:17` has a placeholder comment for one that was never implemented; instead `isAuthenticated()`/`isPlatformAdmin()` logic is copy-pasted independently in `src/routes/index.tsx:16-40` and again (differently shaped) in `src/utils/authUtils.ts:12-61`. Matters because auth/session state has no single source of truth — a future change to the cookie shape (e.g. renaming `data.user.is_platform_admin`) requires hunting down every duplicate instead of updating one hook.
- **Dead password-login code path.** `useLogin`/`login()` (`src/features/auth/api/useLogin.ts:12-17`, `auth.ts:35-37`) is fully implemented but has zero call sites — the only shipped login flow is OTP-based (`Login.tsx` → `useLoginWithOTP`). Matters because it's unclear whether password login was deprecated or is mid-migration; either way it's dead surface area that must still be kept type-correct and reviewed, for no product benefit.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling, unsafe assumptions)
- **Hardcoded fake device fingerprint.** `OtpForm.tsx:106` sends `device_fingerprint: 'admin_panel'` as a literal string for every user, every device, every login — not an actual fingerprint. Matters because the backend's session/device model stores this value per-session (`brello_server` `session.entity.ts`) specifically to support future new-device detection; a constant value makes every login look like the same device, silently defeating that mechanism even if the backend is later wired up to use it.
- **Misleading OTP resend timer display.** `OtpForm.tsx:210-212` renders `` `Resend code in 10:${timeLeft < 10 ? `0${timeLeft}` : timeLeft}s` `` where `timeLeft` is a plain seconds counter initialized to `29` (`OtpForm.tsx:35,60`) — the hardcoded `10:` prefix makes the countdown read like "10 minutes 29 seconds" when it is actually a ~29-second cooldown. Matters because it visibly misinforms users about how long they must wait before resending.
- **No client-side attempt cap on OTP submission.** `submitOtp` (`OtpForm.tsx:102-132`) will re-submit on every 6-digit entry with no tracking of prior failed attempts within the session (only the *resend* action has a cooldown, `timeLeft`/`handleResend`, `OtpForm.tsx:35,51-65`) — a user (or script) can keep entering codes indefinitely from the browser with no local friction. Matters as defense-in-depth: combined with the backend having no rate limiting either (per `brello_server/docs/Module Gaps/auth.md`), there is no friction anywhere in the stack.
- **No accessible labels on the 6 OTP digit inputs.** `OtpForm.tsx:166-179` renders six bare `<input>` elements with no `aria-label`/`aria-describedby` distinguishing digit position, and no `role`/live region announcing verification errors beyond a visual `<span>` (`OtpForm.tsx:188-198`). Matters for screen-reader users, who would hear six indistinguishable "edit text" fields.

### Technical (SECURITY — token storage, session expiry/refresh, logout cache clearing — accessibility, test coverage)
- **Access token (and refresh token) stored in a JS-readable, non-`HttpOnly` cookie — functionally equivalent to localStorage for XSS purposes.** `setCookie`/`getCookie` (`src/utils/cookieUtils.ts:15-18,3-14`) write/read via plain `document.cookie`; `OtpForm.tsx:111` and `LeadForm.tsx:43` call `setCookie('auth_response', JSON.stringify(data))` storing the **entire** `LoginResponse` — including `access_token` **and** `refresh_token` (`authType.ts:73-74`) — in a cookie any injected script can read with `document.cookie`. This is the single biggest gap: the backend already implements a proper `HttpOnly` refresh-token cookie (`cookie.service.ts`, confirmed in `brello_server/docs/Module Gaps/auth.md`) and `src/lib/axios.ts:113` calls `/auth/refresh` with `withCredentials: true` relying on that separate, safe cookie — meaning the `refresh_token` value the frontend duplicates into the JS-readable `auth_response` cookie is not even used by the refresh flow, it's purely extra exposed attack surface with no offsetting benefit.
- **No proactive session-expiry handling.** `expires_in` is present on `LoginData` (`authType.ts:76`) and returned by the login/refresh responses, but is never read anywhere in the webapp (confirmed via repo-wide search) — the app only discovers expiry reactively, when a request 401s and `src/lib/axios.ts:88-131` kicks off a silent refresh. Matters because there is no proactive warning/refresh-ahead-of-expiry, so a user mid-form-fill can have their token expire and only find out when the next API call fails.
- **`useLogout` clears the cookie but never clears the React Query cache.** `src/features/auth/api/useLogout.ts:14-25` calls `removeCookie('auth_response')` and navigates to `/auth/login` on both success and error, but never calls `queryClient.clear()`/`queryClient.removeQueries()` on the module-singleton `queryClient` (`src/lib/react-query.ts:3-10`) that every feature hook shares. Matters on a shared device: because navigation is client-side (SPA, no full reload), any query still within its `staleTime` (default 60s app-wide, `react-query.ts:6`) can continue to serve the previous user's cached data (profile, employee lists, notifications, etc.) to whoever logs in next in the same browser tab.
- **No forgot/reset-password UI despite the backend and shared types supporting it.** `ResendOtpRequest.purpose` includes `'RESET_PASSWORD'` (`authType.ts:35`) but no route, component, or call site in `src/features/auth/` or `src/routes/` ever uses that purpose or links to a reset-password flow — confirmed no `forgot`/`reset-password` references anywhere in `src/`. Matters because password reset is unreachable from the UI (users can only reach `LOGIN`/`LEAD_VERIFICATION` OTP purposes today), even though the backend module fully implements it.
- **Zero test coverage.** No `*.test.*`/`*.spec.*` files exist anywhere under `src/features/auth/`, and no `test` script exists in `package.json`. Matters because this is the highest-blast-radius feature in the app (every route depends on its cookie/token contract) with no automated regression protection at all.

## 5. Top 3 Priorities

1. **Stop storing `access_token`/`refresh_token` in a JS-readable `document.cookie`.** Since the backend already issues a proper `HttpOnly` refresh cookie that the refresh flow already relies on (`src/lib/axios.ts:113`), the frontend should keep the access token in memory only (e.g. inside a real `AuthContext`) and drop `refresh_token` from what it persists client-side entirely — this closes the largest XSS-exposure surface in the module for close to zero functional cost.
2. **Call `queryClient.clear()` in `useLogout` (and on any forced-logout path in `src/lib/axios.ts`'s `handleUnauthorizedClient`).** One-line fix that prevents cross-user data leakage via React Query cache on shared devices/browsers.
3. **Introduce a real `AuthContext`/`useAuth` and delete the duplicated cookie-parsing logic in `src/routes/index.tsx` and `src/utils/authUtils.ts`.** Consolidates the single source of truth for session state, making the token-storage fix in #1 and future changes (e.g., wiring a real device fingerprint, adding session-expiry handling) a one-place change instead of a multi-file hunt.
