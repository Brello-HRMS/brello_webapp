# Module: Payroll (webapp)

## 1. Purpose & Current Usage

The frontend payroll feature covers **payroll configuration and salary assignment only** — it does not implement any payroll *run* (prepare/validate/process/lock/disburse) or payslip UI at all.

What exists, by file:

- **API layer**: `src/features/payroll/api/payrollApi.ts` — wraps 13 endpoints: cycle config (`/configurations`), component master CRUD (`/component-master`), PF config (`/statutory-pf-config`), salary template CRUD (`/salary-templates`), employee list/salary structure/history (`/employees`, `/employees/:id/salary`), and a dry-run simulator (`/simulations/dry-run`). No endpoints exist for payroll runs, payslips, or disbursement.
- **Config page**: `src/pages/payroll/PayrollConfigPage.tsx` (route `organisation/payroll`, gated by `ModuleCode.ORG_PAYROLL`) — accordion of 4 sections: Payroll Cycle Setup (`PayrollCycleSetup.tsx`), Statutory PF (`StatutorySetupPF.tsx`), Salary Components (`SalaryComponents.tsx` + `AddComponentModal.tsx`), Salary Templates (`SalaryTemplates.tsx` + `CreateSalaryTemplateModal.tsx`).
- **Employee payroll listing**: `src/pages/payroll/PayrollEmployeesPage.tsx` (route `payroll/listing`, gated by `ModuleCode.PAYROLL_OVERVIEW`) — table of all employees with Annual CTC, Monthly CTC, Gross, Deductions, Take Home (`src/features/payroll/columns/employeePayrollColumns.tsx`).
- **Employee detail / salary assignment**: `src/pages/payroll/PayrollEmployeeDetailPage.tsx` (route `payroll/listing/:employeeId`) — assign/update an employee's salary structure inline (`SalaryEditPanel.tsx`, `ComponentGrid.tsx`), plus a separate modal path via `AssignSalaryModal.tsx` and a standalone `DryRunModal.tsx` for previewing calculations.
- Routes wired in `src/routes/adminRoutes.tsx:22-24, 101-106, 253-268`.

**Not present anywhere in `src/`**: no payroll-run wizard, no run-status view, no "Process/Lock/Disburse" actions, no payslip list/view/download component. Confirmed via repo-wide search (`grep -ril "payslip\|payroll.*run\|disburse"` over `src/`) — the only payroll-run-shaped hit is an unrelated audit-log enum string.

## 2. Intended / Ideal Usage

- Admin configures payroll cycle, PF, components and templates once (org-level) — this part is implemented.
- Admin assigns/updates salary structures per employee, previewing via dry-run before committing — implemented, with reasonable UX (preview panel, residual-component auto-adjust, exceeding-CTC warning).
- Admin then triggers a payroll run for a period, watches it move through prepare → validate → process → lock → disburse with live status, and can retry/cancel a stuck run — **not implemented in the frontend at all**.
- Employees view and download their payslips once a run is disbursed — **not implemented in the frontend at all**.
- All money-mutating actions (assign salary, create run, process run) should be disabled while in flight and surface both success and failure to the user.

## 3. Cross-Module Connections

- **Depends on**: Employee directory/department data (for the employee picker/filter), RBAC (`RequireAccess` + `ModuleCode.ORG_PAYROLL` / `ModuleCode.PAYROLL_OVERVIEW`), shared `DataTable`, `Dialog`, `Select`, `MultiSelect` UI primitives.
- **Depended on by**: nothing yet — since there is no payroll-run or payslip surface, no notification/audit-log UI hooks into payroll events either (consistent with backend having zero notification calls per `brello_server/docs/Module Gaps/payroll.md`).
- **Missing connection (the one asked about)**: because the run wizard doesn't exist, the question "does the UI poll a stuck `PROCESSING` run and offer retry" and "is there a double-clickable Process button" are both moot — there is no run-triggering UI surface for the backend's process/lock/disburse endpoints to be double-clicked or polled in the first place. The double-processing race and permanently-wedged `PROCESSING` status documented on the backend currently have **no client at all**, webapp or otherwise, so today they can only be hit via direct API calls (e.g. Postman, a script, or a future consumer) — but the instant a run-wizard UI is built without safeguards, it inherits both backend bugs immediately.
- Salary-assignment mutations that *do* exist (`AssignSalaryModal`, `SalaryEditPanel`) correctly disable their submit buttons while pending (see `AssignSalaryModal.tsx:159`, `SalaryEditPanel.tsx:110`), so at least that slice is double-submit-safe.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)
- **No payroll-run or payslip module exists** — the entire "prepare/validate/process/lock/disburse" wizard and payslip view/download described in the task brief is unbuilt on the frontend. Evidence: `src/features/payroll/api/payrollApi.ts:1-169` has zero run/payslip endpoints; `src/routes/adminRoutes.tsx:253-268` only registers `payroll/listing` and `payroll/listing/:employeeId`. This is the single biggest gap — without it, the backend's stuck-`PROCESSING`/double-processing-race bugs have no UI trigger yet, but also admins have **no way to actually run payroll or employees to see payslips** from this app at all.
- Two parallel, duplicated code paths exist for "assign salary": `AssignSalaryModal.tsx` (used nowhere currently — no `import` of it was found outside its own file) versus the inline `SalaryEditPanel.tsx` flow used by `PayrollEmployeeDetailPage.tsx:205-238`. `AssignSalaryModal` and its preview-result renderer duplicate ~80 lines of logic already in `PayrollEmployeeDetailPage`/`AssignSalaryModal` (`DryRunResultPanel` in `AssignSalaryModal.tsx:35-80` vs `ResultPanel` in `DryRunModal.tsx:33-101`) — dead/unreferenced component that should be removed or wired up.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling)
- **Employee payroll listing pagination is broken past page 1.** `PayrollEmployeesPage.tsx:62-64` passes `pagination`, `onPaginationChange`, and `pageCount` to `DataTable` but never sets `manualPagination` (compare with `UsersPage.tsx`, `DepartmentPage.tsx`, etc., which all pass `manualPagination` explicitly). `DataTable.tsx:32` defaults `manualPagination = false`, so `@tanstack/react-table` computes `getPageCount()`/`getCanNextPage()` from the client-side slice of the already-server-paginated `data` array (only the current page's ~10 rows) instead of from the passed `pageCount`. Result: `table.getCanNextPage()` is always false once there's more than one page of employees, so **the Next button in `Pagination.tsx:44-48` is permanently disabled and admins can never see employees beyond the first page.** Compounding this, `PayrollEmployeesPage.tsx:64` passes `pageCount={page}` (the *current page number* from `EmployeeListResponse.page`, `payrollConfigTypes.ts:113`) instead of a computed total-pages value (`total`/`pageSize`) — even fixing `manualPagination` alone wouldn't fix pagination without also fixing this. This affects real payroll data visibility for any org with >10 employees.
- **CTC "must be positive" validation is unreachable in practice.** `payrollSchema.ts:77-80` (`assignSalarySchema`) defines `ctc: z.union([z.string().min(1,...), z.number().positive(...)])`. Since the CTC `<Input type="number">` is bound via `react-hook-form`'s `register` (`AssignSalaryModal.tsx:203`, `SalaryEditPanel` uses plain string state), the field value is always a **string**, so validation always matches the first union branch (`z.string().min(1)`), which only checks non-empty length — not numeric-ness or positivity. A user can type `-50000` or non-numeric text and pass client validation; `Number(data.ctc)` (`AssignSalaryModal.tsx:138`) then sends a negative/NaN CTC to the salary-assignment endpoint. Same pattern in `dryRunSchema` (`payrollSchema.ts:84-94`). This is a real-money input with effectively no client-side sanity check.
- **Salary-component and salary-template create/edit silently swallow failures.** `usePayrollConfig.ts:68-144` — `createComponentMutation`, `updateComponentMutation`, `createTemplateMutation`, `updateTemplateMutation`, `updateSettingsMutation`, `updatePfConfigMutation` all lack an `onError` handler (contrast with `useAssignSalary`/`useDryRun` in `useEmployeePayroll.ts:37-38, 66-68`, which do `toast.error(...)`). Worse, `AddComponentModal.tsx:105-108` and `CreateSalaryTemplateModal.tsx:133-134` call `onSave(data); onClose();` **without awaiting** the (async) save handler, and `PayrollConfigPage.tsx:141-164, 171-188` (`handleAddComponent`, `handleCreateTemplate`) have no `try/catch`. Net effect: if a create/update request fails (validation error, duplicate name, network blip), the modal closes immediately and the user sees no error at all — they believe the component/template was saved when it wasn't. Only the delete flows (`confirmDeleteComponent`, `confirmDeleteTemplate`, `PayrollConfigPage.tsx:129-139, 200-210`) have proper try/catch + toast.
- **No double-submit protection on Add/Edit Component or Create/Edit Template Save buttons.** `AddComponentModal.tsx:129-131` and `CreateSalaryTemplateModal.tsx:165` render a plain `<Button variant="primary" onClick={handleSubmit(onSubmit)}>Save</Button>` with no `disabled` state at all (no `isCreating`/`isUpdating` from `usePayrollConfig` is even passed into these modals). A fast double-click can fire two create requests for the same component/template. (By contrast, `AssignSalaryModal.tsx:159` and `SalaryEditPanel.tsx:110` do correctly disable while pending — the protection pattern exists in the codebase but wasn't applied consistently to the config CRUD modals.)
- **Statutory PF config form has zero validation.** `StatutorySetupPF.tsx:35-52` uses raw `<Input type="number">` with `onChange={(e) => handleChange(key, Number(e.target.value))}` and no zod schema, no min/max bounds. An admin can type `120` for "Employee Contribution (%)" or a negative "Minimum Salary Threshold" and it saves via `handleSaveAll` (`PayrollConfigPage.tsx:85-108`) without any warning — this is an org-wide statutory config that (per the in-app copy) "creates a new versioned config" affecting all future PF deductions.

### Technical (performance, security, accessibility, test coverage)
- **Zero automated test coverage.** No `.test.` / `.spec.` files exist anywhere under `src/features/payroll/` or `src/pages/payroll/` (35 source files, 0 tests) for a feature that computes and displays real compensation figures and writes salary-assignment records.
- **Compensation data exposure is table-stakes-only.** `employeePayrollColumns.tsx:36-76` renders every employee's Annual/Monthly CTC, Gross, Deductions, and Take-Home in one flat, unmasked table gated only by a single coarse `ModuleCode.PAYROLL_OVERVIEW` permission (`adminRoutes.tsx:257`) — there's no row-level or field-level restriction (e.g., a manager-scoped view showing only direct reports), so any role granted that one module flag sees the whole org's compensation data.
- No loading/error state differentiation in `usePfConfig`/`usePayrollSettings`/`useSalaryComponents`/`useSalaryTemplates` beyond `isLoading` — `error` is returned from each hook but never rendered anywhere in `PayrollConfigPage.tsx`, so a failed initial fetch just shows stale/empty accordions with no message.

## 5. Top 3 Priorities

1. **Build the missing payroll-run and payslip UI** (or explicitly scope it out with a documented plan) — right now there is no way for an admin to run payroll or for an employee to see a payslip from this webapp, and any future implementation must proactively guard against the backend's known stuck-`PROCESSING`/double-processing-race bugs (poll with backoff, disable Process on click, surface a Retry/Cancel action for wedged runs) rather than inheriting them.
2. **Fix the broken pagination on `PayrollEmployeesPage`** (`manualPagination` missing + wrong `pageCount` value in `PayrollEmployeesPage.tsx:58-65`) — this silently hides all employees past the first page of a page that exists specifically to review payroll-relevant compensation data.
3. **Make CTC/salary-assignment validation and error handling trustworthy**: fix the unreachable positive-CTC check in `payrollSchema.ts:77-80`, add `onError` toasts to the component/template/settings mutations in `usePayrollConfig.ts`, and add `disabled`/pending guards to the Add/Edit Component and Template Save buttons — today a failed save can look identical to a successful one, and duplicate submissions aren't blocked.
