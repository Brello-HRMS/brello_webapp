# Module: Leave (webapp)

## 1. Purpose & Current Usage

- `src/features/leave/` is a **narrow, admin/config-only** slice of the leave domain. It contains exactly two things:
  1. **Org-wide leave policy configuration** — `LeaveRulesCard.tsx` (total annual days, approval-required toggle, max/month, half-day, backdating, sandwich rule) and `LeaveTypesCard.tsx` (per-type day allocation + accrual mode), both driven by `leaveConfig.schema.ts` (zod) and assembled in `src/pages/leave/LeaveConfigPage.tsx`. Data flows through `useLeaveConfig.ts` → `src/api/leaveConfig.ts` → `PUT/POST /leave-configs*`. Routed at `organisation/leave-config` (`src/routes/adminRoutes.tsx:143-146`), linked from the org setup guide (`src/features/dashboard/components/SetupGuide/SetupGuide.tsx:58,150`).
  2. **Read-only per-employee balance display** — `useLeaveBalance.ts` + `api/leaveBalanceApi.ts` (`GET /leave-balances/employee/:id`), consumed only by `LeaveBalanceCard.tsx` (`src/features/employee/components/EmployeeDetail/LeaveBalanceCard/LeaveBalanceCard.tsx:3,61`), which renders donut charts on the Employee Profile page (`src/pages/Employee/Profile/EmployeeProfilePage.tsx:18,117`).
- There is **no leave-request submission form and no approval queue anywhere in `leave/`**. That entire workflow (list/filter requests, approve/reject modal, org-wide balance table, per-employee balance adjustment) lives in the sibling `src/features/leave-management/` directory, rendered by `src/pages/attendance/LeaveRequestsPage.tsx` and `src/pages/attendance/LeaveManagementPage.tsx`. Confirmed no `overlap`/date-range validation, no approve/reject code, and no tests exist under `src/features/leave/` or `src/pages/leave/` (`find ... -iname "*.test.*"` → empty).
- **`leave/` vs `leave-management/` split**: this does not read as an intentional layered split (e.g. "policy" vs "operations") so much as an accidental one — `leave/` owns *both* a config-CRUD screen *and* a balance-fetching hook, while `leave-management/` independently re-implements balance fetching (`LeaveBalanceView.tsx`, `EmployeeBalanceModal.tsx` via `src/hooks/useLeaveBalances.ts`) and owns the request/approval UI. There is no shared code between the two directories; they duplicate the balance-fetch concern instead of sharing it (see Structural gaps).

## 2. Intended / Ideal Usage

- Config screen: admin sets total leave once, allocation across types always sums to the total (enforced today), and errors on save clearly reflect *why* a save failed.
- Balance display: a number that accurately reflects policy (allocated + accrued + carry-forward − used − pending), with enough context (e.g., accrual type, next accrual date) that a low number is legible rather than alarming or silently wrong.
- Given the backend gap (accrual computed once at balance creation, never re-derived), the ideal UI would surface accrual cadence/next-accrual info or at least not present a stale number with the same confidence as a correct one.

## 3. Cross-Module Connections

- **Depends on**: `src/api/leaveConfig.ts` (`/leave-configs*`), `src/features/leave/api/leaveBalanceApi.ts` (`/leave-balances/employee/:id`), shared UI kit (`components/ui/Input`, `components/ui/Select`, `components/common/ToggleButton`), `react-hook-form` + `zod`.
- **Depended on by**: `src/pages/leave/LeaveConfigPage.tsx` (routed), `src/features/employee/.../LeaveBalanceCard.tsx` (Employee Profile page). Nothing in `leave-management/` imports anything from `leave/` — the two are entirely disjoint at the code level despite covering overlapping domain concepts (leave types/rules configured in `leave/` presumably shape what `leave-management/`'s request form should allow, but there's no shared type or client between them to guarantee that).
- **Missing/expected connections — notification**: Within `leave/`'s scope there is no approve/reject/submit action at all (that lives in `leave-management/`), so there's no misleading "approver notified" confirmation *here*. A quick check of `leave-management/components/RequestDetailsModal.tsx:33-38` shows `approveRequest`/`rejectRequest` mutations call `onClose()` on success with no toast, no success message, and — consistent with the backend having zero notification calls — nothing implying anyone was notified. So the UI isn't actively lying about notification, but it also gives the actor no explicit confirmation of anything beyond the modal closing, which is easy to misread as "done and handled."
- **Missing/expected connections — accrual bug visibility**: `LeaveBalanceCard.tsx:86-121` builds its donut/counter display purely from `available_days`/`consumed_days` off `LeaveBalanceRow` (`src/features/leave/types/leaveBalanceTypes.ts:6-22`), which includes `accrued_days` in the type but **never displays it, never shows accrual cadence, and never distinguishes "monthly accrual not yet caught up" from "you've used most of your leave."** Given the backend computes `accrued_days` once at balance creation and never re-derives it, an employee whose balance was created in January would see a low `available_days` number here with the exact same visual confidence (solid donut, plain number) as a correct balance — there is no affordance (tooltip, subtext, warning icon) that would let a user or admin suspect the number is an artifact of a computation bug rather than genuine leave usage.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)

- **`leave/` vs `leave-management/` duplication, not delineation.** Two independent implementations of "fetch an employee's leave balance from `/leave-balances/employee/:id`" exist: `src/features/leave/api/leaveBalanceApi.ts:5-9` + `src/features/leave/hooks/useLeaveBalance.ts` (wrapped `{success,data}` response type, no `leave_year` param) vs `src/api/leaveBalances.ts:100-110` + `src/hooks/useLeaveBalances.ts:40-46` (`useEmployeeLeaveBalance`, flat response type, supports `leave_year`). Matters: two response-shape contracts for one endpoint will silently drift the next time the backend payload changes — one call site will break while the other appears fine, and there is no single source of truth for "what does a leave balance look like on the frontend."
- **Confusing hook name collision.** `src/features/leave/hooks/useLeaveBalance.ts` exports `useLeaveBalance(employeeId)` (fetches by *employee* id) while `src/hooks/useLeaveBalances.ts:63-69` also exports a same-named `useLeaveBalance(id)` that fetches by *balance-record* id (`GET /leave-balances/:id`, used for admin ledger/adjustment). Matters: identical export names with different semantics across two modules is a real trap for future edits — an import-path typo silently swaps "this employee's balance" for "an arbitrary balance record."
- **Config and balance concerns share one feature folder with no internal boundary.** `src/features/leave/` mixes an admin-config form (`components/`, `schemas/`) with an unrelated employee-balance data hook (`api/`, `hooks/`, `types/`) that has nothing to do with configuration; there's no `index.ts` or clear submodule boundary signaling these are two separate concerns bundled under one name.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling)

- **Error-shape mismatch makes `useLeaveConfigQuery`'s "config doesn't exist yet" handling dead code, and breaks user-facing error messages.** `src/features/leave/hooks/useLeaveConfig.ts:18-26` catches errors and checks `(error as ApiError).response?.data?.message` to decide whether to swallow the error and return `null` ("configuration does not exist yet"). But `src/lib/axios.ts:139-141`'s response-error interceptor rejects with a **flat** object `{message, status, data}` (via `parseApiError`, `src/lib/axios.ts:36-49`) — there is no `.response` key on the rejected value. So `error.response` is always `undefined`, the `if` never matches, and the code always falls through to `throw error` — meaning the intended "treat 404 as no-config-yet" branch never actually executes for any error type. The same broken shape assumption is used in `useSaveLeaveConfigMutation`'s `onError` (`useLeaveConfig.ts:68-71`): `error.response?.data?.message` is always `undefined`, so every save failure shows the generic fallback `'Failed to save configuration'` toast instead of the real backend validation message. Matters: admins get no actionable error text when a config save fails for a real reason (e.g. a validation rule from the backend), which is exactly the kind of "silent failure" pattern this audit is looking for.
- **`LeaveConfigPage` only checks `isLoading`, never `isError`.** `src/pages/leave/LeaveConfigPage.tsx:41,90-92` destructures only `data`/`isLoading` from `useLeaveConfigQuery()`; a genuine load failure (network error, 500, permission issue) renders the form with blank defaults with no indication anything went wrong, and — combined with the bug above — a subsequent save would call `createLeaveConfigDraft` (POST) as if no config exists, risking creation of a duplicate/conflicting leave config for an org that already has one.
- **No client-side allocation-mismatch guard beyond the final zod `refine`.** `leaveConfigSchema` (`src/features/leave/schemas/leaveConfig.schema.ts:33-48`) only rejects submission if `sum(leaveTypes.days) !== totalLeave`; the live badge in `LeaveTypesCard.tsx:50-52` and `LeaveRulesCard.tsx:44-48` shows the mismatch but nothing disables the Save button proactively — a user can click Save repeatedly and get bounced by the same toast (`LeaveConfigPage.tsx:80-88`) rather than the button being disabled until allocation matches.

### Technical (performance, accessibility, test coverage)

- **Zero test coverage.** No `*.test.*`/`*.spec.*` files exist anywhere under `src/features/leave/` or `src/pages/leave/` — none of the schema `refine` logic, the config-save orchestration (draft-create → update → activate, 3 sequential network calls in `useLeaveConfig.ts:36-63` with no rollback if step 2 or 3 fails), or the balance-display aggregation math in `LeaveBalanceCard.tsx` is verified.
- **No accessibility attributes.** `grep -n "aria-\|role="` across `src/features/leave/components/*.tsx` and `src/pages/leave/*.tsx` returns zero matches — the toggle switches, remove-leave-type icon buttons (`LeaveTypesCard.tsx:118-127`), and the number-input rows have no `aria-label`s, relying entirely on visual adjacency to convey meaning to screen readers.
- **Partial-failure risk in the 3-step save.** `useSaveLeaveConfigMutation` (`useLeaveConfig.ts:36-63`) performs create → update → activate as three sequential awaited calls with no compensating action; if `updateLeaveConfig` or `activateLeaveConfig` throws after `createLeaveConfigDraft` succeeded, a draft config record is left behind with no id surfaced back to the UI (the mutation throws before returning `currentId`), so a retry will call `createLeaveConfigDraft` again rather than resuming the existing draft.

## 5. Top 3 Priorities

1. **Fix the error-shape mismatch in `useLeaveConfig.ts`** (`response?.data?.message` vs the actual flat `{message,status,data}` rejection) — this silently breaks both the "no config yet" detection and every save-failure toast, so admins currently never see real validation errors when leave policy setup fails.
2. **Consolidate the duplicated employee-balance fetch path** (`features/leave/api/leaveBalanceApi.ts` + `hooks/useLeaveBalance.ts` vs `src/api/leaveBalances.ts` + `src/hooks/useLeaveBalances.ts`) into one client/hook — two independently-typed clients hitting the same endpoint will drift and break independently as the backend response shape evolves.
3. **Add an accrual-context affordance to `LeaveBalanceCard.tsx`** (e.g. show accrual cadence or a "balance grows monthly" note) — given the backend's accrual-freeze bug already inflates or deflates real balances silently, the frontend currently presents a low number with full visual confidence and no way for an employee or admin to tell a bug apart from genuine low leave.
