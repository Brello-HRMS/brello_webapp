# Module: Audit (webapp)

## 1. Purpose & Current Usage

- **Org-admin viewer**: `src/pages/audit/AuditPage.tsx` — a filterable, paginated list of audit events for the logged-in organization. Renders stat tiles (total events, top module, creates, deletes) via `useAuditLogStats`/`useAuditFilterOptions` (`src/features/audit/hooks/useAuditLogStats.ts`), a `DataTable` of rows (`src/features/audit/columns/auditColumns.tsx`), and a slide-over detail drawer (`src/features/audit/components/AuditDetailDrawer/index.tsx`) with a before/after diff view (`src/features/audit/components/AuditDiffViewer/index.tsx`).
- **Platform-admin viewer**: `src/pages/audit/PlatformAuditPage.tsx` — same shape, plus an organization filter (`useOrganizationsList`), hitting `/platform/audit-logs*` endpoints instead of `/audit-logs*` (`src/features/audit/api/audit.api.ts:12-13`).
- **Data layer**: `src/features/audit/api/audit.api.ts` wraps 8 endpoints (list, stats, filter-options, entity-history — each duplicated org vs platform). Hooks in `src/features/audit/hooks/useAuditLogs.ts` and `useAuditLogStats.ts` are thin React Query wrappers.
- **Routing/permissions**: Org route `audit-logs` is gated by `RequireAccess module={ModuleCode.AUDIT_LOG}` (`src/routes/adminRoutes.tsx:338-344`). Platform route `audit-logs` has **no** access guard at all (`src/routes/platformAdminRoutes.tsx:39`) — unlike the org side, any authenticated platform-admin session can hit it (though this matches the pattern of all other platform routes in that file, so it isn't audit-specific negligence).
- **Nav**: org sidebar entry is server-driven (`useSidebarMenu`, gated by the same `AUDIT_LOG` permission); platform sidebar entry is hardcoded in `src/features/sidebar/Sidebar.tsx:93-97` (`PLATFORM_ADMIN_MENU`), always shown to platform admins.
- **Dead code**: `useEntityHistory` (`src/features/audit/hooks/useEntityHistory.ts`) and its backing `getEntityHistory` API call (`src/features/audit/api/audit.api.ts:33-36`) are never imported anywhere outside the audit feature itself (verified via repo-wide grep) — there is no "view history" affordance on any entity detail page (employee profile, leave request, payroll run, etc.), so a fully-built per-record audit trail capability is unreachable from the UI.

## 2. Intended / Ideal Usage

A production audit-log viewer should: (a) let admins filter by every module/action the backend actually emits, with the UI's own filter list acting as ground truth for coverage; (b) render diffs that degrade gracefully for partial/missing before-after payloads; (c) support paging/searching efficiently over a table that can grow unbounded; (d) surface entity-level history inline on the record itself (e.g., "view audit trail" on an employee or payroll record) rather than only as a standalone global log; (e) offer export/download for compliance review. This module gets (b) mostly right and has the API surface for (d) but never wires it up.

## 3. Cross-Module Connections

- **Depends on**: `ModuleCode.AUDIT_LOG` (`src/enum/modules.ts:47`) for RBAC gating; `components/common/DataTable`, `Select`, `DatePicker`, `Dialog` for presentation; `features/platform/organizations` for the org filter dropdown on the platform page; backend `/audit-logs*` and `/platform/audit-logs*` REST endpoints (list/stats/filter-options/entity-history).
- **Depends on it**: nothing else in the frontend — no other feature imports from `src/features/audit/*` (confirmed by grep: only the two page files and the feature's own internals reference `AuditLogModule`/`AuditAction`). The `useEntityHistory` hook is exported but has zero consumers.
- **Missing/expected connection**: no entity-detail page (employee, leave request, payroll, role, etc.) links to or embeds an audit-history panel, even though the backend and frontend both already support `entity/:type/:id` history lookups (`getEntityHistory`). This is the single largest "built but unused" gap in the module.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)
- **Entity-level history is unreachable from the product.** `useEntityHistory`/`getEntityHistory` (`src/features/audit/hooks/useEntityHistory.ts:7`, `src/features/audit/api/audit.api.ts:33-36`) exist end-to-end but have no UI consumer anywhere in `src/pages` or `src/features` outside the audit feature itself. Matters because the most useful audit UX — "who changed this record and when" from the record's own page — was built at the API/hook layer and then never surfaced, wasting the investment and leaving admins to filter the global log manually by entity type/id instead.
- **Near-total duplication between org and platform audit UI.** `AuditPage.tsx` and `PlatformAuditPage.tsx` are ~90% identical (same filters, same stat-tile layout, same drawer), differing only in the org-filter dropdown and API base path. There is no shared `AuditLogView` component; any future change (e.g., adding an export button) has to be made twice. Matters because it's a straightforward source of drift (already visible: the two pages show different stat tiles — "Creates/Deletes" vs "Logins/Failed Logins" — with no shared config for which stats to show).

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling, unsafe assumptions)
- **Module filter list silently understates the badge/color config's own coverage.** `AuditModuleBadge`'s `MODULE_COLOR_MAP` (`src/features/audit/components/AuditModuleBadge/index.tsx:5-26`) has no entries for `BILLING`, `SUBSCRIPTION`, `CLIENT`, `PROJECT`, `DOCUMENT`, `HR_TEMPLATE`, `HOLIDAY`, or `COMPANY_POLICY` even though all are defined in `AuditLogModule` (`src/features/audit/enums/audit-log-module.enum.ts:1-31`) — these fall back to a generic `'default'` grey badge. Matters because it means the enum was extended (presumably to anticipate billing/subscription audit events) but the viewer was never updated to visually distinguish them, a small but telling sign the module list is aspirational rather than fully wired.
- **Search input is not debounced.** `AuditPage.tsx:118-122` and `PlatformAuditPage.tsx:131-135` call `setSearch(e.target.value)` directly on every keystroke, which flows straight into `queryParams` (memoized) and triggers a new React Query fetch per character typed. Matters for a table that can hold a very large number of rows — every keystroke round-trips to the backend.
- **No client-side guard against `date_from > date_to`.** Both pages pass `dateFrom`/`dateTo` straight through to the query params (`AuditPage.tsx:39-40`, `PlatformAuditPage.tsx:39-40`) with no validation that the range is sane before hitting the API.

### Technical (performance, accessibility, test coverage)
- **No debounce + fixed 20-row page size compounds request volume**, but pagination itself is at least server-side (`manualPagination`, `pageCount = Math.ceil(meta.total / meta.limit)` — `AuditPage.tsx:167-175`), so the core list is not at risk of loading unbounded rows; the risk is req-volume from the search box above, not payload size.
- **No test coverage**: no `*.test.tsx`/`*.spec.tsx` files exist anywhere under `src/features/audit/` or `src/pages/audit/` (confirmed via directory listing) — none of the diff-rendering edge cases (missing old_value, missing new_value, empty changed_fields) are covered by automated tests, despite `AuditDiffViewer` containing meaningful conditional logic (`isCreate`/`isDelete`/`isUpdate` branches, noise-field filtering).
- **Diff viewer itself handles malformed data reasonably well**: `AuditDiffViewer` (`src/features/audit/components/AuditDiffViewer/index.tsx:75`) early-returns when both `old_value` and `new_value` are null, and falls back to `Object.keys({...old_value, ...new_value})` when `changed_fields` is empty, so it does not crash on partial payloads — this is a place the module gets defensive coding right, not a gap.

## 5. Top 3 Priorities

1. **Wire up entity-level audit history** (`useEntityHistory`) into at least one high-value entity page (employee profile, payroll run, or role) — the backend and hook already support it; right now it's fully dead code and the single biggest missed opportunity in the feature.
2. **Debounce the search input** in both `AuditPage.tsx` and `PlatformAuditPage.tsx` — trivial fix, currently generates one API call per keystroke against what is meant to be a large, append-only table.
3. **Extract a shared `AuditLogView` component** used by both `AuditPage` and `PlatformAuditPage` (parameterized by API base and optional org filter) to eliminate near-duplicate logic and prevent the two views from silently drifting further (as already happened with the stat-tile choices).
