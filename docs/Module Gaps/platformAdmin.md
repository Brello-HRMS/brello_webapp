# Module: Platform Admin (webapp)

## 1. Purpose & Current Usage
- `src/features/platformAdmin/` contains **55 directories and zero files**. Confirmed via `find src/features/platformAdmin -type f` (and `-type l` for symlinks) returning no results at all — this was independently re-verified twice to rule out a shell/glob artifact.
- The directory tree mirrors a fully planned feature-module layout: `plans/`, `leads/`, `roles/`, `tenants/`, `defaults/`, `templates/`, `apps/`, `billing/`, `analytics/`, each with the standard `types/`, `components/`, `hooks/`, `api/`, `validation/` subfolders, and even specifically-named leaf component folders such as `plans/components/PlanFormModal/`, `plans/components/ModuleSelector/`, `leads/components/LeadStatusBadge/`, `roles/components/RoleFormModal/`, `roles/components/PermissionsMatrix/`, `tenants/components/TenantStatusBadge/`, `templates/components/TemplateFormModal/`, `billing/components/ChangePlanModal/`. Nothing was ever implemented inside any of them.
- **Nothing imports from this directory.** `grep -rl "platformAdmin" src` outside `src/features/platformAdmin/` itself only matches `src/routes/index.tsx` and `src/routes/platformAdminRoutes.tsx` — and those two files reference the *route namespace* `platformAdminRoutes`/URL prefix, not the `features/platformAdmin` module. Their actual page imports (`src/routes/platformAdminRoutes.tsx:1-17`) all come from `src/pages/platform/*`, e.g. `PlatformLeadsPage`, `PlatformPlansPage`, `PlatformRolesPage`.
- Those page files in turn import their logic from the **sibling** directory `src/features/platform/` — e.g. `src/pages/platform/PlatformLeadsPage.tsx:6-11` imports `usePlansList`/`useLeadsList`/`useUpdateLeadStatus`/`Lead`/`LeadStatus` from `../../features/platform/plans/hooks` and `../../features/platform/leads/*`; `src/pages/platform/PlatformPlansPage.tsx:13-20` imports `usePlansList`, `useDeletePlan`, `useEnterprisesList`, `PlanFormModal`, `Plan` from `../../features/platform/plans/*` and `../../features/platform/enterprises/hooks`.
- So the actual, live lead-management and plan-management UI (which does exist and is routed/used, per the separate `platform/` audit) lives entirely in `src/features/platform/`, not `src/features/platformAdmin/`.
- **`platformAdmin/` vs `platform/` split**: from directory listing alone, `src/features/platform/` has the same domain areas (`plans`, `leads`, `roles`, `organizations`, `enterprises`, `departments`, `designations`, `industryTypes`, `appModules`, `apps`, `billing`, `dashboard`, `planPermissions`, `actions`) fully populated with real files (45 `.ts*` files found), while `platformAdmin/` has the near-identical shape (`plans`, `leads`, `roles`, `tenants`, `defaults`, `templates`, `apps`, `billing`, `analytics`) completely empty. This strongly suggests `platformAdmin/` was either (a) scaffolded for a planned rename/restructure of `platform/` that was never carried through, or (b) generated by a code-gen tool/template and abandoned before implementation. Either way it is dead weight today, and the near-duplicate naming is confusing for anyone navigating the codebase (an unrelated audit of "platform admin" functionality could easily start in the wrong directory, as this task's original framing did).

## 2. Intended / Ideal Usage
- Given the folder shape, the intended usage mirrors `features/platform/`: per-domain modules (leads, plans, roles, tenants, billing, analytics, templates, defaults, apps) each exposing `types`, `api` (query/mutation hooks or fetch functions), `hooks` (composed state), `components` (presentational + modal pieces like `PlanFormModal`, `RoleFormModal`, `ChangePlanModal`), and `validation` (schema validation for forms) — consumed by pages under `src/pages/platform/`.
- Ideally there should be exactly one implementation per domain concept. If `platformAdmin/` was meant to supersede `platform/`, the migration should have been completed (move logic in, repoint the `pages/platform/*` imports, delete the old directory) rather than left as an empty shell alongside the working one.

## 3. Cross-Module Connections
- **Depends on**: nothing — there is no code to depend on anything.
- **Depended on by**: nothing — confirmed no file outside `src/features/platformAdmin/` imports from it.
- **Missing/expected connections**: N/A for this directory specifically, since it's inert. The functionally-equivalent connections (routes → `pages/platform/*` → `features/platform/*` → backend `lead`/`plan` endpoints) all run through `features/platform/`, which is being audited separately. For completeness: this webapp module does **not** itself call the backend `lead`/`plan` endpoints described in `brello_server/docs/Module Gaps/lead.md` and `plan.md` (only `features/platform/` does), so the "unauthenticated backend privilege-escalation" risk noted there is not attributable to `platformAdmin/` — it belongs entirely to the `platform/` audit.

## 4. Gaps

### Structural (architecture, component boundaries, coupling, missing abstractions)
- **Entire directory is an empty, unimplemented duplicate scaffold of `src/features/platform/`.** Evidence: `find src/features/platformAdmin -type f` → 0 results across all 55 subdirectories (`src/features/platformAdmin/plans`, `/leads`, `/roles`, `/tenants`, `/defaults`, `/templates`, `/apps`, `/billing`, `/analytics`, and their `types`/`components`/`hooks`/`api`/`validation` children). This matters because it is pure dead weight in the repo, it doubles the cognitive load for anyone trying to find where lead/plan/role/tenant logic actually lives, and it risks a future contributor accidentally building real code in the wrong (unwired) directory.
- **Confusing naming collision with `src/features/platform/`.** The two directories cover the same domains (`plans`, `leads`, `roles`, `apps`, `billing` in both; `tenants`/`defaults`/`templates`/`analytics` only in `platformAdmin`, `organizations`/`enterprises`/`departments`/`designations`/`industryTypes`/`appModules`/`dashboard`/`planPermissions`/`actions` only in `platform`). Given a separate agent audit was dispatched specifically to `platform/`, this naming overlap is a real, demonstrated source of confusion, not a hypothetical one.

### Coding (bugs, dead code, inconsistent patterns, missing validation/error handling, unsafe assumptions)
- **The whole directory is dead code by definition** — there is no logic to review for bugs, validation, or error handling because there is no logic. Flagging as a "coding" gap only in the sense that an empty, unreferenced directory tree checked into the repo is itself a form of clutter that should be either finished or removed.

### Technical (performance, security, accessibility, test coverage)
- **No security exposure from this directory** — since it contains no API calls, it cannot itself give false confidence about the lead/plan backend endpoints being protected. That false-confidence risk (frontend routes gated only by client-side role checks while backend `LeadController`/`PlanController`/`PlanModuleController` are only `JwtAuthGuard`-gated, per `brello_server/docs/Module Gaps/lead.md` and `plan.md`) applies to `src/features/platform/` + `src/pages/platform/*`, which is out of scope here but should be cross-referenced in that audit.
- **No test coverage** — trivially true since there is no code, but worth noting: zero `.test.ts(x)` or `.spec.ts(x)` files exist anywhere under `src/features/platformAdmin/`.

## 5. Top 3 Priorities
1. **Decide the fate of `src/features/platformAdmin/` and act on it** — either delete the entire empty scaffold (lowest-risk, immediate clarity win) or, if a genuine migration off `src/features/platform/` was planned, resource and complete it; leaving 55 empty directories in place indefinitely serves no one.
2. **If keeping both names conceptually, rename one of them** — `platform/` (populated, live) and `platformAdmin/` (empty) are one keystroke apart and cover overlapping domains; this is exactly the kind of ambiguity that caused this audit to need an explicit clarifying note, and will keep costing new contributors time until resolved.
3. **Cross-link this finding into the `platform/` audit** — since the real lead-management and plan-management UI (and the associated backend-authorization false-confidence risk flagged in `brello_server/docs/Module Gaps/lead.md`/`plan.md`) lives in `src/features/platform/`, ensure that audit's document carries the security finding, since this document (`platformAdmin.md`) is not the right home for it.
